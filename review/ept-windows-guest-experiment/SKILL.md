# Windows 客户机实验（Windows Guest Experiment）

可复用的宿主机到 Windows 客户机（Host-to-Windows-Guest）工作流参考。技能是候选方法而非任务权威：当前用户请求、适用的项目契约和观察到的环境共同决定目标与语义。当本工作流与上述因素冲突时应进行适配，不要机械地执行每一个参考章节。

## 按需选择参考文档

在进行虚拟机工作之前，若有可用的只读预检（preflight）则先使用它，并且只阅读所选动作需要的运行手册/适配器章节。当金丝雀测试（canary）或操作失败时，阅读失败路由（failure-routing）参考。当修改本工作流或解释其来源时，阅读模式（patterns）参考。对于改变状态的操作，请保留用户的范围、目标标识、回滚边界和证据要求。

仅当当前平台没有原生的持久化任务/运行状态，且任务受益于备用记录时，才使用 assets/run-record.example.json。使用该备用方案时，请用 scripts/validate-run-record.py 对其进行校验。

对于可复用的数据工作流，在创建运行目录或选择数据适配器之前，先阅读 references/upstream-sources.md，再阅读 references/data-plane.md。仅当选择了对应适配器时，才阅读 references/capesolo-mcp.md、references/debugger-stack.md 或 references/behavior-capture.md。这些参考文档中提到的脚本是本地胶水入口点；不要凭记忆重建它们的协议或文件布局。

## 自主性策略

当下一个动作是只读、可逆或已被验证过的操作契约覆盖时，继续自主执行。

仅在以下至少一项成立时停止并请求人工输入：

- 缺少所需凭据；
- 目标、虚拟机、基线或授权/范围无法唯一确定；
- 破坏性操作可能抹掉仅存的证据；
- 某个非幂等操作的状态未知（UNKNOWN）且无法安全调和；
- 两个均有效的下一步动作在证据或保全后果上存在实质性差异，而任务本身未在二者之间做出选择。

不要仅仅因为一次传输失败、一条命令没有标准输出、或某个首选工具缺失就停止。应路由到下一个已验证的适配器，或对该运行进行分类。

## 可复用的执行原则

1. 当平台原生任务状态、重试、租约/CAS、结果服务器和产物 API 可用且符合项目契约时，优先使用它们。不要在已有的持久化编排器之外另建一套运行时协议。
2. 在插桩之前，先从当前任务/项目契约中确定真实目标和可观察的验收标准。
3. 每次真实启动都使用唯一的 RUN_ID。绝不复用失败的运行目录。
4. 在真实目标之前，先用无害的金丝雀测试证明控制（Control）、数据（Data）、长运行器生命周期和所需插桩均可用。
5. 将控制（Control）、数据（Data）与完成（Completion）视为相互独立的事实。
6. 改变状态的操作在派发前必须有验证方法。断连后，先将其调和为 APPLIED / NOT_APPLIED / UNKNOWN 再重试。
7. 在宿主机/平台实际取得文件之前，客户机上报的文件不构成证据。
8. 自然观察、启动后附加（attach-after-launch）和调试器启动观察属于不同的运行。
9. 超时、传输丢失、缺少标准输出或插桩失败都不意味着业务结果为负。
10. 在回滚、关机或破坏性清理之前先完成产物收集（harvest）。
11. 一个可变的虚拟机/调试会话只有一个写入者。使用真正的原子原语，而不是 JSON 属主字段。
12. 面向仓库的记录必须脱敏。运行时标识符可以临时存在于本地执行中，但未经清理不得提交。
13. 当某个适配器已定义命令时，不要发明新命令。如果本地工具语法因版本而异，先查询本地帮助，并将该差异记录为环境事实。
14. 执行客户机操作时，以可执行运行手册和随附的适配器脚本作为默认关口。自定义包装器不能替代控制、数据、长运行器、GUI 会话或插桩金丝雀测试。
15. 备用运行记录只有在填入其真实验收标准和持久化完成事件、且随附校验器通过之后才有效。初始化占位符和生成的文件不构成证据。
16. 如果本地 Windows 脚本被执行策略阻止，仅对受信任的本地脚本使用进程级策略覆盖；绝不要静默更改持久策略，并记录该环境差异。

## 可复用数据工作流的边界

共享工作流只负责宿主机/客户机控制、数据采集、完成状态、工具金丝雀测试、恢复和通用执行有效性。它不负责样本身份、许可/授权含义、分支干预、响应来源或项目特定的业务验收。这些由项目以显式配置文件的形式提供。

规范通用序列为：

`preflight -> run record -> writer lock -> baseline -> control canary -> data canary -> long-runner canary -> interactive-session canary (if GUI-dependent) -> instrumentation canary -> launch -> observe -> harvest -> outcome -> release`

每个箭头在 references/data-plane.md 中都有一个命名的后置条件。缺失后置条件会将运行保持在 INCONCLUSIVE、INVALID_INSTRUMENT 或 INFRA_FAILURE；不得用模型推断来填充。

## 必需的最终结果

对于通用工作流报告，将每次运行归入以下宽泛类别之一：

这些标签仅用于判定执行有效性。它们不替代项目特定的结果字段，也不定义运行的业务含义。

- POSITIVE（阳性/成功）
- NEGATIVE（阴性/失败）
- INCONCLUSIVE（无法定论）
- INVALID_INSTRUMENT（插桩无效）
- INFRA_FAILURE（基础设施失败）

不要编造超出运行手册允许范围的更强结论。
