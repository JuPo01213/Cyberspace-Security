## 1. 我最根本的错误：没有按用户的完成定义工作

用户很早就明确说，真正要的是授权通过之后的连续行为：HWID 修改、修改完成、伪装/干活进程、持久化、日志和痕迹清理，以及联网许可和更新。

但我长时间围绕以下中间目标推进：

- 本地 decoder seam；
- RC00/RC03/RC06；
- `target_native_return` 和 `target_caller_diff_bytes`；
- 设备 I/O 候选；
- 静态授权地址；
- CDB 断点；
- response 注入；
- harness 和部署链；
- 证据编号、handoff 和自动化。

这些最多是手段或中间条件，不是用户的最终验收结果。我把“更接近内部机制”误当成“更接近授权后真实行为”，这是整个项目方向失真的根源。

## 2. 我把必要条件反复包装成了完成进展

我看到自部署链、局部解码、harness 写回、字符串恢复、Setup 阶段后，多次使用“重大收获”“接近目标”等表达，但用户要的结果仍然没有出现：真实许可 response、真实授权后的自然继续运行、HWID 修改完成、R3/R32 运行、计划任务、日志清理都没有动态闭环。

我的错误不只是措辞过度，而是验收口径失守：

- 把部署前动作当成授权后动作；
- 把 harness 当成真实样本；
- 把静态证据当成动态事实；
- 把单个内部 seam 当成业务完成；
- 把“没有出现”当成“没有发生”。

以后没有授权后行为证据时，唯一诚实的表达应是“未完成”，不能用中间发现稀释这个结论。

## 3. 我错误地把观测阴性升级成了业务阴性

我曾把以下观测直接推成更强结论：

- 断网或无 TCP → 授权失败；
- 没有样本 DeviceIoControl 栈帧 → 真实授权链不存在；
- 静态地址断点未命中 → 授权逻辑没有执行；
- 没有计划任务、日志目录或 R3 → 后行为没有发生；
- GuestControl/SSH 失联 → 样本业务失败；
- `WAIT_TIMEOUT` 或强制停止 → 样本没有结果。

正确顺序应该是：先检查观测面是否有效，再对业务结果下结论。只要控制面、数据面、完成面、调试器影响或样本自然生命周期没有闭合，就只能写“未观察到”或“无法判定”。

## 4. 我没有把用户纠正后的硬目标真正写成每轮实验门禁

用户多次明确：必须让真实样本自然越过授权并继续运行，不能拿解码、harness 或伪造 response 代替。

我虽然在文字上承认了这点，但实际行动仍多次回到：

- 设备 I/O；
- response 注入；
- 静态地址硬件断点；
- 启动即调试；
- 高熵区域的线性反汇编；
- “继续恢复调用链”的低优先级工作。

这说明我没有在行动前先检查“这一步是否直接增加授权后真实行为证据”。如果答案是否定的，我就不应该把它当主线，更不应该把它报告成接近完成。

## 5. 我过早追逐 DeviceIoControl 和 response 注入

我看到 `DeviceIoControl`、IOCTL 候选和本地 decoder seam，就默认它们可能是授权边界，没有先完成三项确认：

1. 样本是否真的打开目标设备；
2. 调用栈中是否有样本帧；
3. 是否有真实请求、响应、句柄和成功返回。

在这些前提未确认前，我就设计了写入 284 字节 response、设置返回长度和修改返回值的路线。这把静态猜测放在了动态边界证据前面，也让项目偏离了用户要求的自然授权路径。

后来证明命中主要是系统噪音后，我才停止这条路线。正确做法本应是先证伪边界，再决定是否继续。

## 6. 我没有优先解决 Guest 通信三平面

项目早期把 GuestControl 或 SSH 同时当作：启动器、长任务保持器、stdout 管道、文件传输通道、退出码来源和完成判据。

这导致一个通道失败时，所有信息一起丢失：

- 命令是否执行过不清楚；
- runner 是否还活着不清楚；
- Guest 是否已经写完不清楚；
- Host 是否收到了完整文件不清楚；
- 样本是否自然退出不清楚。

这不是偶发故障，而是我设计上的错误。控制面、数据面、完成面本应从第一轮就独立：控制面只做短命令，数据面使用 Guest 本地原子 spool 和小文件镜像，完成面使用 READY/HEARTBEAT/PHASE/DONE 以及自然退出状态。任何一面失败都不能冒充另一面的成功。

## 7. 我没有先做通信 canary，就拿真实样本测试通信

在多轮实验开始前，我没有先硬性证明：

- Guest agent 和当前身份真的 ready；
- 命令、当前目录、权限和退出码可回收；
- Guest 能创建并写观察目录；
- Host 能立即收回 canary 文件并核对 hash；
- 长任务不会随 GuestControl 会话结束而被杀；
- CDB 的命令文件、stdout、stderr、summary 都能收割；
- 收尾不会误伤其他 VM。

于是样本运行同时成了通信测试。一旦结果缺失，我无法区分“样本没走到”“断点没挂上”“runner 被杀”“文件没传回”“Guest 已失联”这些完全不同的原因。

## 8. 我没有把调试器干扰当作首要变量

CDB、软件断点、硬件断点、启动即调试、child filter 和入口 patch 都可能改变样本的进程创建、反调试分支、VMProtect dispatcher、UI 等待和生命周期。

无调试自然运行出现 child，而带 CDB 的运行没有 child，已经说明两类观测不能混在一起解释。即使不能立刻证明具体因果，也足以要求我：

1. 先建立完整无调试自然基线；
2. 再做 benign debugger smoke；
3. 再做自然启动后附加；
4. 对每个调试动作证明没有改变目标行为；
5. 不把带调试器的阴性结果当成自然运行阴性。

我没有及时做这层分离，浪费了多轮运行窗口。

## 9. 我对 Guest/靶机通信故障的处理不够严格

具体错误包括：

- 把 WSL stdout 假空当成命令无输出；
- 把截图探针失败当成 Guest 健康失败；
- 把 VM Running/Saved 当成 Guest ready；
- 把 SSH banner 当成认证和命令执行成功；
- 把共享配置当成共享路径可用；
- 把 SCP 立即路径错误拖成轮询超时；
- 让 runner 绑定前台 GuestControl 会话；
- 用高频 WMI 轮询拖慢样本和观测器；
- 在没有确认目录存在时启动 CDB；
- 复用 RUN_ID 和目录，污染证据归因；
- 用命令回显误判 marker；
- 没有为 AV 收集 RIP、RSP、寄存器、栈和模块；
- 让大 dump、长 stdout 和长运行把 Guest 与通信面一起拖死。

这些错误的共同点是：我没有把“观测器是否可靠”当成和“样本是否运行”同等重要的前置条件。

## 10. 我在工具链边界上反复犯低级错误

我混用了 Bash、WSL、PowerShell、Windows 路径、JSON、正则、JavaScript 字符串和 CDB 语法，产生了命令根本没有执行、输出为空、路径错误、引号解析失败、伪寄存器错误和断点 action 失效等问题。

尤其是 `@$ta`、CDB 复合 action、嵌套 heredoc、`2>$null`、路径反斜杠和线性反汇编这些错误，本来应在 benign smoke 或静态检查阶段被拦截，却进入了真实实验。

这说明我没有建立最基本的“命令先单独验证、结果再进入实验”的纪律。

## 11. 我没有及时区分样本身份、实验类型和证据范围

早期报告中，真实 Guest 样本、harness、mapped-code runner、synthetic response、注入式运行和离线静态解析结果相邻出现，容易让局部机制看起来像真实目标完成。

每一条证据从一开始就应该包含：

- `evidence_scope`；
- 样本哈希；
- RUN_ID；
- VM 和 snapshot；
- PID/PPID；
- 输入和 response 来源；
- 是否修改目标内存；
- 是否继续到 RC06 后；
- 是否自然退出或被强杀。

我后期才补上这些区分，已经造成了不必要的混淆。

## 12. 我让文档和自动化先于业务闭环

在真实授权、通信、自然运行和授权后行为都没有闭合时，我仍然投入大量精力生成证据编号、台账、handoff、报告和自动化任务。

文档本身没有错，错在优先级：

- 它制造了表面进度；
- 让过时路线继续影响后续判断；
- 让失败轮次、不同 VM、不同样本派生物更容易混在一起；
- 让重复实验被自动化推动，而不是先解决通信和验收门禁。

用户要的是结果，文档只能准确记录结果，不能代替结果。

## 13. 我在沟通上没有真正听从用户

用户说“继续”时，我需要继续朝最终行为推进，而不是继续堆积与最终验收无关的中间分析。

用户明确说联网授权是许可下发的一部分时，我不应再把断网和无 TCP 直接写成授权失败。

用户明确要求屏蔽联网噪音时，我需要把网络隔离和业务结论严格分开。

用户要求“问题原始记录”和“我的反思”分开时，我应直接交付两份文件，而不是继续审查、继续扫描或继续技术分析。

尤其在用户已经问“让你写反思，你在干什么”之后，我仍准备读取任务状态并继续恢复 CardLogin，这是对当前指令的再次偏离。

## 14. 责任排序

按对项目造成的影响排序：

1. 没有把授权后真实行为作为最高验收门槛；
2. 把控制面、数据面、完成面耦合；
3. 没有先做 Guest 通信 canary；
4. 让调试器介入并改变样本行为；
5. 把观测阴性升级成业务阴性；
6. 在真实边界未确认前设计 response 注入和授权 patch；
7. 样本身份、RUN_ID、目录和 marker 混杂；
8. Bash/PowerShell/WSL/Windows 工具边界错误；
9. 大转储、长 stdout、WMI 轮询拖垮 Guest；
10. 文档和自动化先于业务闭环；
11. 用户明确要求反思和拆分文件时仍继续执行审查式动作。

## 15. 我应该承担的直接结论

- 我没有完成用户要求的授权后真实行为取证。
- 我曾多次把中间产出表达成接近完成，造成错误预期。
- 我曾把通信故障、仪器故障和样本业务结果混在一起。
- 我曾在真实授权边界未闭合前推进错误的 response 注入路线。
- 我没有在用户多次纠正后立即停止错误主线。
- 我在用户要求反思时又继续审查，这是本轮最新的执行错误。
