# AGENTS.md

## 适用范围

本文件适用于整个 `Cyberspace-Security` 仓库。

所有 Agent 在进行调研、方案设计、技术选型、架构建议、工作流设计、实验总结和文档撰写时，都必须遵守以下证据与表述规则。

## 核心原则：不要把模型推演伪装成实践经验

任何由模型基于训练数据、公开资料、逻辑推理、组件能力或工程常识自行组合出来的方案，都必须明确标注为：

- 候选方案；
- 模型综合建议；
- 推导方案；
- 待验证方案；
- 未经本项目实测。

不得因为方案“看起来合理”“组件本身成熟”“符合常见工程原则”，就把整个组合描述为：

- 成熟工作流；
- 久经考验；
- 生产最佳实践；
- 已经过实践验证；
- 行业标准方案；
- 推荐架构；

除非有直接证据支持这些结论。

**组件成熟，不等于组件组合成熟。**

**官方提供，不等于长期实践验证。**

**技术可行，不等于实际可靠。**

**模型能推导出来，不等于现实中有人这样长期使用过。**

---

## 强制证据分层

所有重要技术结论尽量标记其证据层级。

### A. 可直接验证的事实

来自：

- 官方文档；
- 官方源码；
- 官方发布记录；
- 项目维护者明确说明；
- 可复现的接口或行为；
- 本仓库已经实际执行并验证的结果。

可以使用明确事实语气，但仍应提供来源或测试记录。

示例：

> REMnux MCP Server 支持 SSH mode。

如果来自官方文档，应给出来源。

---

### B. 外部实践证据

来自：

- 真实部署案例；
- issue / discussion 中有细节的实际使用记录；
- 公开技术报告；
- 研究论文；
- 企业或团队公开工程实践；
- 社区长期可重复出现的实践经验。

必须区分：

- 单个案例；
- 多个独立案例；
- 广泛实践。

不能把一个 GitHub issue 或一篇博客自动升级成“行业共识”。

---

### C. 有依据的推断

根据已知事实进行合理推理，但没有直接实践证据。

必须使用类似措辞：

- “可以推测”；
- “理论上可行”；
- “从接口能力看可以这样组合”；
- “值得尝试”；
- “可能适合”；
- “候选方案”。

禁止直接写成既成事实或最佳实践。

---

### D. 模型综合方案

由 Agent 自行把多个工具、项目、接口或工程原则组合成新的整体方案。

必须显式标记：

> **该方案为模型基于公开资料和逻辑推演形成的综合方案，当前没有证据证明这一完整组合已经经过长期实际使用或生产验证。**

如果没有亲自部署和端到端测试，还必须补充：

> **未经本项目实测。**

这是本仓库非常重要的规则。

---

### E. 本项目实测结果

只有实际执行过，才能标记为“已实测”。

实测至少记录：

- 环境；
- 版本；
- 配置；
- 测试输入；
- 执行步骤；
- 结果；
- 失败项；
- 已知限制；
- 日期。

“安装成功”“服务启动”不等于完整工作流验证成功。

只有完成目标场景的端到端验证，才能写：

> 本项目已验证该流程在上述环境中可运行。

即便如此，也不要把一次测试扩展成：

> 该方案在所有环境中稳定可靠。

---

## 对“成熟”“最佳实践”等词的使用限制

以下词语属于高证据要求措辞：

- 成熟；
- 久经考验；
- 最佳实践；
- 行业标准；
- 生产级；
- 广泛验证；
- 稳定可靠；
- 主流工作流；
- 标准架构。

使用这些词之前，Agent 必须能回答：

1. 谁在实际使用？
2. 使用了多久？
3. 是否有多个独立来源？
4. 是否与本文描述的是同一个完整方案，而不仅仅是其中某个组件？
5. 是否存在直接公开证据？

如果不能回答，就降低表述强度。

例如：

错误：

> 这是一个成熟的 AI 逆向工作流。

更准确：

> 该组合由若干长期使用的逆向工具和较新的 AI/MCP 接入方式组成。完整组合目前应视为候选集成方案，需要实际验证。

---

## 禁止“借成熟度”

严禁以下推理：

```text
REMnux 很成熟
+
Ghidra 很成熟
+
CAPE 很成熟
+
MCP 能连接它们
=
REMnux + Ghidra + CAPE + MCP 是成熟工作流
```

这是无效推导。

正确表达：

```text
各底层组件有各自的使用历史
+
存在相应接口
=
从技术能力上存在组合可能性

完整组合是否可靠
=
需要单独寻找实践证据或自行实测
```

## 调研输出要求

对于架构、工作流和技术选型类调研，优先采用以下结构：

### 已确认事实

只写有直接证据支持的内容。

### 已有公开实践

列出现实中能找到的实际案例，并注明证据强弱。

### 推断与候选方案

明确告诉读者这是分析和推演，不是既有事实。

### 未验证部分

主动列出：

- 没有找到实践证据的部分；
- 尚未测试的部分；
- 可能存在兼容性问题的部分；
- 模型不确定的部分。

### 验证计划

如果方案值得尝试，给出最小实验，而不是直接给它贴“成熟”标签。

---

## 对来源的要求

优先级：

1. 官方文档 / 官方源码；
2. 维护者 issue / discussion / release notes；
3. 论文、会议材料、公开技术报告；
4. 有完整环境和步骤的实践文章；
5. 社区讨论；
6. 模型自身知识。

模型自身知识只能作为搜索线索或推理基础，不能伪装成外部实践证据。

如果某个关键结论只来自模型记忆或推理，必须说明。

---

## 调研与设计的边界

Agent 可以提出新方案，也应当主动提出可能更优的组合。

问题不在于“不能创新”，而在于必须如实标注它是什么：

- 已有实践；
- 参考实现；
- 推断；
- 新设计；
- 实验性方案。

不要为了让文档显得权威，而模糊这些边界。

---

## 对后来维护者负责

写文档时假设：

> 三个月后，一个完全不了解当前对话背景的人会把这份文档当成事实依据。

因此必须避免让后来的人误以为：

- 某套方案已经有人完整跑过；
- 某个架构是行业通行做法；
- 某个组合已经证明稳定；
- 某个建议来自真实工程经验；

除非确实有证据。

**宁可明确写“目前不知道”“没有找到证据”“这是我们的候选设计”，也不要制造虚假的确定性。**

---

## 实施后的状态升级

一个候选方案可以随着证据增加升级状态。

建议使用：

```text
[推断]
    ↓
[候选方案]
    ↓
[局部测试]
    ↓
[本项目端到端实测]
    ↓
[重复验证]
    ↓
[有外部实践证据]
```

每次升级必须有相应记录。

禁止只通过修改措辞把方案从“候选”升级为“成熟”。

---

## 本仓库默认表达标准

如果无法证明完整工作流已经经过现实实践，默认写：

> 这是基于现有工具能力、公开资料和工程推理形成的候选方案。底层组件可能已有较长使用历史，但当前组合方式本身不因此自动获得相同的成熟度。除非另有实测记录，本方案应视为未经本项目端到端验证。

这一规则优先于为了简洁、宣传效果或文档权威感而使用更强的措辞。
