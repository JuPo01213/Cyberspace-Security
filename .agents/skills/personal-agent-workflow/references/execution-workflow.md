# Execution Workflow

## 共享生命周期

复杂任务通常经过以下阶段，但低风险任务可以合并或跳过阶段：

```text
Frame → Discover → Choose → Execute → Verify → Close
```

### Frame

确定唯一主目标、当前阶段、输出消费者、完成证据、已知约束和真正阻塞。用户给出的实现方式是线索，不自动成为唯一方案；用户明确要求的交付和限制仍然是当前契约的一部分。

### Discover

读取工作区规则、当前状态和相关资料；检查已有脚本、技能、官方能力和成熟方案。调查只服务于改变路线、解除阻塞或提高完成证据，不把搜索结果堆积成交付物。

### Choose

选择最小充分路线，记录会改变结果的假设和暂定决策。信息获取和方案比较可以主动进行；改变产品方向、扩大范围或执行不可逆动作不能仅由 Agent 单方面承诺。

### Execute

按当前阶段完成动作，保持任务数据、指令和状态分离。每项附加动作都要有契约依据、任务对象、阶段适配和消费者。

### Verify

检查与目标对应的实际状态。验证强度与风险、可逆性、范围和失败影响匹配；不因为“更专业”自动增加哈希、备份、审计、报告、回滚或重复测试。

### Close

只在完成证据足够时收口。报告实际完成、未验证、阻塞和未覆盖范围；把新的可复用经验留在当前任务反馈，除非用户明确维护，不直接改技能。

## 最小路由

- **明确的小改动**：读有效规则 → 定位 → 最小编辑 → 相关检查 → diff/状态确认。
- **新功能或重构**：先建立需求模型 → 发现并评估复用能力 → 设计切片 → 实现 → 测试和结果验证。
- **需求含糊**：主动回读和调查 → 形成候选需求模型 → 只询问仍会改变结果的最小问题；不要一边猜方向一边开始实现。
- **难 bug 或回归**：复现 → 缩小范围 → 提出可证伪假设 → 观测区分 → 最小修改 → 回归；不要连续盲目打补丁。
- **外部事实或协议**：优先第一方来源 → 记录版本/日期/限制 → 在结论足以改变决策时停止。
- **架构维护**：检查当前结构和消费者 → 选择唯一边界 → 小步修改 → 检查调用方和文档 → 必要回归。
- **长线任务**：保持目标、依赖、已完成、未完成、阻塞、证据和下一步；局部通过不自动等于整体完成。

## 主动性与控制权

当用户表达很模糊时，既不要直接选择未确认的长期方向，也不要把所有理解成本原样推回用户。先提供候选模型、调查关键事实和明显取舍，再让用户只决定不可由事实推导的价值选择。

例如“做一个图片编辑工具”可以先区分截图标注、轻量处理和专业工作流，说明各自的范围与成本；在方向确认前不应自行实现一个完整编辑器。若用户已经明确“做一个支持文字和箭头标注的 MVP”，则可以进入执行。

## 收口门禁

以下任一项不足时，不声称整体完成：

- 目标结果没有实际出现；
- 关键文件、工具或状态证据没有捕获；
- 只验证了局部而任务要求整体；
- 测试通过但当前契约仍未满足；
- 有未解释的冲突、阻塞或重大未覆盖范围。

反过来，低风险、局部、可逆的工作不需要为了形式完整运行所有可用检查。验证以足够支持当前结论为准。
