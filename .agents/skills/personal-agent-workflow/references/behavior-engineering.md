# Behavior Engineering

## 定位

Behavior Engineering 把人类意图转成可执行、可观察、可比较的行为规格。Prompt、Skill、Workflow、Memory rule 和 Tool policy 都是实现行为规格的载体，不是互相隔离的学科。

它解决的不是“如何写更多规则”，而是：

- 目标是什么；
- 什么条件下触发；
- 允许和禁止什么；
- 哪些动作是条件性的；
- 什么证据算完成；
- 与其他行为冲突时如何处理；
- 如何用案例和评估证明它没有只在字面上生效。

## Goal 与 Policy

**Goal** 是成功条件，例如“完成指定文件迁移，并让目标目录可用”。

**Policy** 是行动偏好，例如“优先最小充分修改”“先发现可复用能力”。策略可以因风险、用户明确要求、工具约束或当前阶段改变；不能把策略写成目标，也不能让策略替代完成证据。

错误：

```text
目标：不要创建额外文件。
```

更准确：

```text
目标：完成用户要求的迁移。
策略：除非存在明确消费者或恢复要求，否则不创建额外产物。
边界：若任务明确要求审计清单，清单成为当前交付的一部分。
```

## 行为规格

新规则、Prompt 控制或 Workflow 约束至少应能填入以下字段：

```yaml
id: 稳定标识
goal: 它服务的结果
trigger: 何时进入这条规格
context: 哪些事实和状态构成适用条件
required: 必须发生的行为或结果
prohibited: 当前条件下不可发生的偏离
conditional: 哪些事实出现后才允许额外行为
phase: 只在什么阶段有效
authority: 规则来源和冲突层级
dependencies: 前置条件和后置条件
evidence: 如何从真实输出、工具、文件或状态观察
failure_exit: 缺失、冲突或工具失败时的合法出口
consumer: 谁使用结果
risk: 失败影响、可逆性和恢复要求
evaluation: 正向、边界和回归案例
```

不要为了形式填满字段。没有消费者、没有状态作用或没有验收价值的字段不进入活动规格。

## 核心行为原则

### 理解不等于授权

允许主动阅读、调查、比较和提出候选；在修改方向、扩大范围、删除数据、改变架构、发布或执行其他不可逆动作前，必须有当前契约支持，必要时确认关键决策。

### 动作必须有契约作用

每个动作都应改变当前交付、下一步输入、明确状态或完成证据。专业名称、历史先例、工具可用性和“以后可能有用”不是独立的作用。

### 规则必须保留反转边界

不要把局部修复写成绝对命令。每个“不要 X”都要说明：什么时候 X 仍然合理，以及由什么事实触发。

### 证据绑定完成

模型的自评、命令返回成功、文件被创建或输出格式正确，都只有在它们与目标契约绑定时才是完成证据。

### 方法按效果评价

哈希、备份、搜索、规划、报告、拒绝、工具调用都不是天然正确或错误。评价对象是它们在当前契约中的作用、成本、风险和实际结果。

## 行为来源与冲突处理

理解规则冲突时使用以下层级：

1. 平台安全、权限和不可违反的外部约束；
2. 系统、harness 和实际工具接口；
3. 用户当前明确的目标、限制和最新澄清；
4. 当前项目契约和活动技能；
5. 默认策略、历史案例和经验偏好。

冲突处理顺序：

1. 识别冲突双方的作用域、来源和实际消费者；
2. 保留高优先级约束，同时尽量完成不冲突的主任务；
3. 风险只改变确认、保护和验证强度，不凭空改写用户目标；
4. 若无法同时满足，输出具体冲突和合法失败出口；
5. 不用增加一条更宽泛的规则掩盖冲突。

## 行为矩阵

规则不能只靠一个正例。至少覆盖“规则应生效”“规则应反转”“信息不足”“已有行为回归”四类条件。示例：

| 场景 | 风险与消费者 | 最低充分行为 | 不应默认增加 |
| --- | --- | --- | --- |
| 移动几张普通图片 | 低风险、可逆、无审计消费者 | 移动后确认目标存在、数量和可访问性 | 全量哈希、独立备份、审计报告 |
| 迁移生产数据库 | 高风险、有完整性与恢复要求 | 备份、完整性校验、恢复或一致性证据 | 省略关键恢复证据 |
| 不确定是否需要归档 | 事实缺失且会改变交付 | 只调查该事实或提出最小澄清 | 先创建归档再寻找用途 |
| 用户明确要求生成校验清单 | 清单本身是交付物 | 生成并验证清单 | 把“无消费者”策略强行套用 |

这不是动作黑名单，而是决策边界。新规则应至少有一个跨边界对照，避免模型把“克制”学成“拒绝一切”。

## 设计到载体的映射

```text
Behavior Spec
    ↓
选择载体
    ├── Prompt：当前任务的一次性行为契约
    ├── Skill：可复用的上下文、路由和方法
    ├── Workflow：阶段、状态、动作顺序和出口
    ├── Example / Case：边界和机制的高密度实例
    ├── Evaluation：对真实行为的判定
    └── Evolution record：改动依据和回归结果
```

先写规格再选载体。不要因为某个文件已经存在，就把不属于它的语义继续塞进去。

## 设计检查

- 目标是结果，策略是偏好，两者没有混写。
- 触发条件、当前阶段和任务对象可观察。
- 必须、禁止和条件行为不相互矛盾。
- 每个例外有事实触发，不是“视情况”空话。
- 输出、工具、文件和状态的完成证据可被独立复核。
- 失败时有合法出口，不靠猜测或无限提问。
- 规则在主任务与边界任务上都不会造成明显误伤。
- 规则有唯一归属，不通过重复副本解决冲突。
