# 从实践经验到 Skill 指导

本参考用于处理最容易造成 Skill 过拟合的问题：**经验值得复用，但证据还不足以成为普遍指令。**

## 先判断当前文字是什么

### 解释性知识

解释性文字主要回答：

- 发生过什么；
- 为什么值得注意；
- 当前证据支持到哪里；
- 哪些仍然未知；
- 哪些条件下可能相关。

它增加判断信息，但不自动要求 Agent 执行新步骤。

例：

> 某次 Guest Agent 的初始 prompt 被截断，但 Agent 后续自行读取完整文件，因此最终报告成功不能证明初始 delivery 成功。

这是一条真实经验，不等于“以后所有任务都必须做 prompt SHA-256 比较”。

### 指令性文字

指令性文字应明确产生执行后果，通常包含：

```text
条件
→ 动作 / 禁止 / 后置条件
→ 跳过或停止条件
```

例：

> 当任务结论依赖某一跨边界交付是否成功时，使用接收端证据判断该边界；不得用后续阶段自行恢复后的成功反推此前边界成功。

这已经抽掉了 Pi、prompt.txt、具体字节数等偶然载体，保留的是可迁移的行为边界。

## 内容应该放在哪里

### Observation / problem slice

保存真实运行事实和证据。

适合：

- 原始失败；
- 当前根因；
- 未确认机制；
- 最小修复；
- 回滚；
- 证据位置；
- “不能由本案例推出什么”。

它不自动构成通用指令。

### Project knowledge / design docs / references

保存：

- 当前项目成立的经验；
- 值得后续任务检索的故障模式；
- 尚未证明普适的假设；
- 设计理由；
- verification status；
- 来源与适用范围。

Agent 可以利用这些知识判断当前情况，但不得因为读到它就自动增加全局 mandatory step。

### Skill guidance

只有当内容已经足够稳定、可迁移，并且确实应该改变这类任务的默认执行行为时，才进入 Skill。

Skill 更适合保存：

- 稳定后置条件；
- 可迁移决策规则；
- 反复出现的边界；
- 真正需要遵循的工作流；
- 明确的禁止性推断。

### Mechanical enforcement

如果一个要求已经是确定、机械、可自动判断的不变量，优先把它固化为：

- schema；
- script；
- test；
- lint；
- CI / hook。

不要把本来可自动保证的东西长期依赖自然语言提醒。

## 一条经验升格前至少检查

不要规定机械的“出现 N 次就升级”。看证据质量，而不是计数。

至少问：

- 是否有真实运行证据，而不只是理论推断？
- 在改变表面载体后，底层机制仍然成立吗？
- 是否存在明确反例或适用边界？
- 它解决的是通用 Skill 缺口，还是项目/adapter/环境问题？
- 写进 Skill 后会不会给无关任务新增成本或前置步骤？
- 能否把事故细节抽掉，只留下稳定的条件与后置条件？
- 当前已有证据时，是否允许复用而不是机械复测？
- 加入该指导后，真实任务或独立 eval 是否有可重复改善？

证据不足时，继续作为知识保存，不要为了“复用”强行升格。

## 失败后的更新顺序

遇到新失败时优先按以下顺序定位：

1. 当前任务事实是否理解错；
2. 当前环境或工具是否失效；
3. adapter / 调用边界是否有局部缺口；
4. reference 是否遗漏解释；
5. example 是否没有覆盖一个细微行为；
6. Skill 的稳定抽象是否真的有误。

只有最后一种情况明确成立时，才优先改通用 Skill。

## 经验可以被看见，但不自动拥有指令权

这是本参考最重要的边界。

仓库可以保存大量高价值经验；Agent 也应该主动检索与当前问题相关的经验。问题不在“是否让模型看到”，而在“看到以后是否自动变成命令”。

历史经验用于提出候选解释和风险；当前任务事实与直接证据用于决定是否适用。
