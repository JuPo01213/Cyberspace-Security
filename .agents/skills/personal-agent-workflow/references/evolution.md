# Evolution Engineering

## 唯一职责

Evolution 负责在有证据、有消费者和有唯一归属的前提下修改行为资产。普通任务、一次运行或一条未经复核的反馈不会自动改写技能。

```text
正常使用
当前资产 + 当前任务 → run / assessment → 最小反馈 → 停止

显式维护
反馈/历史/知识事实 → 单一维护问题 → 候选修改 → 回归 → 保留、拒绝或延期
```

## 维护触发

进入维护至少满足以下之一：

- 用户明确要求审查、重构、补强或优化技能；
- 同一可观察缺口反复出现，且证据足以改变决策；
- 活动接口、案例消费者、外部知识或项目边界发生变化；
- 已定义的维护周期到达，且本次检查有明确消费者。

没有具体偏离时，不凭直觉加长 Prompt、增加字段或新建案例。

## 维护输入

维护只读取当前请求指定或已定义为维护输入的材料：

- 活动技能与其唯一归属文件；
- 相关 `run`、`assessment` 和最小 `feedback`；
- 必要的历史归档；
- 外部知识快照及其来源、取得日期、内容摘要或哈希和用途。

历史材料是证据，不是普通 Prompt 上下文。把事实、推断、建议和未知分开；无法追溯或与当前事实冲突的材料只能作为待调查线索，不能覆盖活动规则。
## 失败归因

先区分问题属于哪一层：

- **行为资产**：目标、边界、阶段、输出契约或控制未表达清楚。
- **上下文**：事实、排序、长度、位置、污染或状态不正确。
- **案例/评估**：没有测试真正的边界，或判定器不能观察目标。
- **harness/runtime**：消息层级、工具、权限、schema、网络或状态有问题。
- **模型能力**：在表达、输入和执行条件都稳定后仍不能完成。
- **用户契约**：目标、范围或完成证据本身尚未确定。

只有第一类问题默认生成 Prompt/Skill 变体；其他问题转交对应组件，不用文字堆叠掩盖。

## 单一维护问题

一次维护只回答一个会改变文件决策的问题：

```text
缺口：观察到什么偏离？
证据：哪次运行、反馈或可靠事实支持它？
消费者：谁会使用修复？
归属：哪个文件/组件拥有这段语义？
保留：哪些原始输入、边界、例外和已有行为不能丢？
修改：最小可证伪的变化是什么？
验收：哪个正常、边界和回归案例能证明它？
停止：什么证据不足时不再继续？
```

“整体更好”“更专业”“更完整”不是维护问题。

## 维护循环

1. 冻结当前版本和 baseline 证据。
2. 写出一个可被运行推翻的偏离假设。
3. 找到唯一语义归属，避免把同一规则复制到多个文件。
4. 只改变一个主要行为变量；若必须组合，明确把结论限定为组合效果。
5. 先更新或新增最小案例/评估，再运行正常、边界和回归检查。
6. 比较行为、成本和主任务完成情况。
7. 只在改善真实缺口且没有不可接受回归时保留；否则拒绝或延期。
8. 记录实际变化、证据和未覆盖范围，然后停止。

## 发布门

一次修改不能因为目标案例通过就自动进入活动技能。至少区分：

- **局部通过**：修改后的指定案例满足契约。
- **相对改善**：同条件下 variant 优于 baseline。
- **边界保持**：触发案例和约束释放案例都没有不可接受退化。
- **回归接受**：与构造例不同的留出案例、主任务和必要成本都在可接受范围内。

只有最后一项满足时，才把候选改动写入活动技能；否则保留为候选、拒绝或等待新的证据。测试输入、评估意图和可能输出不进入生产规则。
## 变体交付

当维护对象是 Prompt 或行为控制时，交付必须保留可比较信息：

```text
baseline_prompt
variant_prompt
changed_variable
held_constant_conditions
baseline_run_and_assessment
variant_run_and_assessment
keep | reject | needs_more_evidence
unverified_scope
```

没有可观测 baseline、variant 或条件差异无法隔离时，只报告两次实际观察，不作因果结论。组合修改只能归因于组合，不把改善归给其中一条未经隔离的规则。
## 反馈格式

反馈只保留能改变下一次维护决策的事实：

```json
{
  "schema": "personal-agent-workflow/feedback-v1",
  "feedback_id": "fb-001",
  "source_run_id": "run-001",
  "source_assessment_id": "assessment-001",
  "gap": "artifact_loss | delivery_ambiguity | target_observation | assessment_mapping | consumer_gap | duplicate_process | route_contamination | coverage_gap",
  "observed_fact": "实际观察到的缺口",
  "affected_consumer": "受影响的流程或使用者",
  "proposed_owner": "唯一应修改的文件或组件",
  "evidence_refs": ["run/output.txt"],
  "status": "candidate"
}
```

没有实际运行、事实、消费者或证据引用的意见只能作为待调查线索，不直接进入活动技能。

## 跨 Skill 混同进化

维护行为资产时，不把当前 Skill 当作封闭系统。若 sibling Skill、problem slice 或其他领域实践已经出现相似机制，允许把它们作为候选证据和反例来源。

跨 Skill 迁移时：
- 迁移底层机制，不机械复制原文、目录或完整流程；
- 区分来源 Skill 的真实证据与目标 Skill 的实际验证；
- 来源中成熟的规则到了新语境仍先作为 candidate；
- 目标 Skill 应使用自己的触发、路由、风险和完成证据表达；
- 同一 Skill 内保持活动规则单一归属，跨 Skill 允许同一机制存在不同适配版本；
- 若同一机制在多个不同载体上得到独立支持，可提高其成熟度，但仍保留明确边界。

具体跨 Skill 迁移流程由 `skill-authoring/references/mixed-evolution.md` 维护；普通使用不为形式全量扫描所有 Skill。

## 防止腐化

- 不因一个案例添加普遍规则；先寻找竞争解释和边界案例。
- 不保留“已经无消费者”的流程、字段、日志、快照或兼容入口。
- 不用文件副本模拟版本历史；使用项目已有版本控制或真实恢复机制。
- 不把历史观察、可能输出和外部建议写成当前事实。
- 不因一次局部通过删除尚未覆盖的高风险行为。
- 不为保持旧接口而保留与当前契约冲突的双轨路径，除非用户明确要求兼容。
- 不在普通任务中读取完整反馈、历史归档或知识快照。

## 结束标准

维护在以下任一情况停止：

- 缺口由局部修改和足够回归验证；
- 证据不足，需要新的真实观察；
- 修改没有消费者或没有改善；
- 新知识与当前事实冲突且无法解决；
- 回归显示已有任务、输入、输出或边界退化。

停止不是失败。准确保留“尚未证明”和下一项低成本证据，比堆叠未经验证的规则更有价值。
