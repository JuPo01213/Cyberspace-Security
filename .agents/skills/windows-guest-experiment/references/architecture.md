# Windows Guest 能力架构

## 从结果倒推能力

先定义任务要证明的后置条件，再选择能产生这些条件的能力。一个任务的最小闭环通常是：

```text
任务契约
  → 能力 profile 与证据有效性
  → 输入/参数交付
  → 执行与监督
  → 原始观测与产物收割
  → 同一运行归因
  → 终态、清理与校准
```

每一箭头都表示可检查的交接，不表示某个固定命令。入口、工具、VM、runtime 和 Agent 都是实现；`run_id`、输入身份、接收方确认、完成事件和目标证据才是跨实现保持的语义。

## 七个平面和各自权威

| 平面 | 负责回答 | 主要证据 | 不能替代 |
| --- | --- | --- | --- |
| 任务 | 要完成什么、何时算完成 | 任务契约、验收字段 | 工具状态 |
| 能力 | 当前入口能提供什么 | registry、版本、限制、验证记录 | 真实任务结果 |
| 交付 | 接收方拿到了什么 | 读回字节、哈希、ack、路径上下文 | 文件已在 Host |
| 执行 | 谁在何处做了什么 | 进程谱系、job/session、调用返回 | 目标行为 |
| 观测 | 真实发生了什么 | 原始 JSONL、日志、artifact、事件 | 摘要和报告 |
| 监督 | 何时继续、收口或重开 | 状态转换、硬截止、决策记录 | 业务完成 |
| 恢复/校准 | 如何保留、清理和改进 | 收割清单、终态、问题切片 | 当前运行的样本结论 |

一个平面的失败只能先归类到该平面。例如 Host 没有收割到文件，先是交付/收割事实；不能直接写成 Guest 没有生成文件或样本业务失败。

## 权威关系

任务契约和项目 overlay 定义语义；能力登记定义能力声明；接收方读回和原始事件定义实际发生；报告、状态、stdout 和模型自述是待核对材料。工具调用成功只说明调用层返回成功，不能自动证明下游消费者已经使用输入。

跨运行材料不得拼接成一个完成链。若输入来自 run A、观察来自 run B、收割来自 run C，必须保持它们的 run 身份，并将整体结论标为未闭合或未知。

## 需要修正的过度约束

- “所有状态都由 Host 持有”应改为：长期项目和最终证据权威在 Host；Guest Agent 可以持有 Guest 内的临时工作状态。
- “成熟 runtime 存在就不能有第二个状态机”应改为：不得建立第二个任务结果权威；允许为通信交接和 Agent 监督建立薄的协调状态。
- “低层工具永远最后”应改为：选择能够证明所需后置条件的最低复杂度路径；成熟入口无法提供必要语义时，薄适配可以提前出现。
- “每次都运行完整 preflight/canary”应改为：只验证本轮实际依赖且证据可能失效的能力。
- “固定轮询间隔”应改为：按心跳、最后事件、预期耗时、硬截止和异常信号自适应检查。
- “Agent 报告有内容就成功”应改为：先验收原始 session、输入投递、Guest 产物和任务后置条件。

## 何时把问题上升为通用改进

一次事故先作为问题切片保留：观察、影响平面、最小区分检查、项目/部署/技能归属、回滚和未解决风险。只有当同一缺口在多个任务、平台或通信 profile 中重复出现，并且不依赖样本语义，才修改通用技能。项目特有的地址、路径、凭据、样本 seam 和证据字段留在项目层。
