# Skill Authoring

把 Skill 当作**可复用的执行指导**，而不是项目事实、历史档案或万能规则集。适用 Skill 被触发后，应指导“怎么做”；用户当前目标、项目事实和同一任务中的直接证据决定这些指导如何实例化。

## 核心原则

### 先复用成熟方法，再决定是否自建

涉及已有成熟生态、工具、工作流或规范时，优先查官方资料、上游实现和经过实践的社区方案。不要因为模型可以手写，就跳过成熟工具。

区分来源和权威范围，不把二次整理称为官方，不把一次本地成功称为成熟实践。需要调研、选型或判断证据成熟度时，读取 [research-and-reuse.md](references/research-and-reuse.md)。

### 区分知识与指令

真实实践中的观察、失败、解释、假设和设计理由可以很有价值，但**被记录不等于有资格命令未来任务**。

- 解释性文字保存事实、原因、风险、适用范围和未知，帮助 Agent 判断。
- 指令性文字定义条件、动作、禁止、后置条件、跳过条件或停止条件，直接改变 Agent 行为。
- 单次 problem slice、单个项目故障或一次成功实现，不自动升级为通用 Skill 规则。
- 已有经验值得复用但尚未证明普适时，优先保存在项目知识、research、design docs 或 reference 中，并明确范围与未验证部分。

需要决定一条经验应停留在哪里、何时升格为 Skill 指导时，读取 [experience-to-guidance.md](references/experience-to-guidance.md)。

### Skill 约束语义，不追求流程外观

优先写稳定的目标、判断边界和后置条件，不把某次事故的修复步骤机械复制成所有任务的固定序列。

如果可信的当前证据已经满足某个后置条件，不要仅为了“按 Skill 跑一遍”而重复验证。与当前任务无关的通用步骤，不得仅因它存在于 Skill 中就成为前置任务。

根据任务脆弱度选择自由度：

- 多种方案都合理 → 写目标、决策标准和边界。
- 存在推荐模式但允许变化 → 写参数化流程或可配置脚本。
- 顺序、权限、安全或正确性高度脆弱 → 使用明确步骤、确定脚本和硬停止条件。

### 保持入口短，按需披露

`SKILL.md` 只保留：

- Skill 的实际能力与适用范围；
- 稳定的核心约束；
- 主要决策路由；
- supporting references 的读取条件。

详细 schema、长流程、案例、背景解释和专项模式放入 `references/`；重复且适合确定性执行的逻辑放入 `scripts/`；用于产出的模板和素材放入 `assets/`。

不要为了“完整”创建没有明确用途的目录、README、速查表或重复文档。

## 创建或更新流程

### 先理解真实任务

先收集或回读几个真实使用情境，确认：

- 用户最终想得到什么；
- 哪些请求应该触发该 Skill，哪些不应该；
- 哪些约束是真正稳定的，哪些只是当前项目事实；
- 当前失败来自 Skill 缺口、项目适配、工具缺失、证据不足，还是执行偏离。

若仓库已有相关 Skill、运行记录、problem slices、review、eval 或历史版本，先读取最相关材料，不从空白假设开始。

### 再规划可复用资源

对每类真实任务问：

1. 从零完成它需要哪些判断与工具？
2. 哪些知识会反复被重新发现？
3. 哪些代码会反复被重新写？
4. 哪些内容只在特定模式需要？
5. 哪些只是一次项目事实，不应进入通用 Skill？

据此决定是否需要 `references/`、`scripts/`、`assets/`。没有明确收益就不创建。

### 写最小有效 Skill

优先保留真正会改变执行决策的信息。

好的 Skill 指令通常能回答：

- **何时适用？**
- **前提是什么？**
- **应该做什么？**
- **什么证据算满足？**
- **何时可以跳过？**
- **何时必须停止或请求信息？**
- **哪些结论不能从当前事实推出？**

避免把背景故事、事故叙述和大量理由直接写成强命令。需要理由帮助判断时，把解释留在 reference，并从 Skill 链接过去。

### Examples 只解决规则难以稳定表达的行为

模型已经能稳定做到的事情，不为了“有 Few-shot”而加 examples。

普通校准优先使用简洁的 **input → desired output**。只有错误答案表面也合理、边界难以纯文字表达时，才使用 contrastive example。

examples 与 evals 必须分开。需要设计或筛选 examples、contrastive cases、cross-carrier eval 和 ablation 时，读取 [examples-and-evals.md](references/examples-and-evals.md)。

### 验证，而不是凭感觉继续加规则

至少检查两类问题：

- **触发问题**：该触发时没触发、不该触发时误触发 → 优先修改 name/description/作用域。
- **执行问题**：触发正确但行为错误 → 优先修改 instruction、reference、example、script 或工具适配。

测试应验证可观察行为和真正的不变量，不要只匹配固定措辞、标题或正则。

出现一次失败后，先修最窄的根因。不要立即新增通用规则；先判断失败是否来自当前任务、环境、adapter、工具或证据解释。

## 经验反馈闭环

真实运行首先产生证据，而不是直接产生规则。

默认顺序：

```text
真实任务
→ observation / problem slice
→ 可复用经验或假设
→ 跨情境验证 / 反例 / eval
→ 稳定执行指导
→ Skill
→ 真正机械的不变量再进入 script / test / lint / CI
```

允许经验被 Agent 看见，但不要让经验自动拥有指令权。

## 完成前检查

提交 Skill 前确认：

- 没有把项目事实写成普遍事实；
- 没有把一次失败修复写成所有任务的固定流程；
- 没有把二手整理误标为官方或成熟实践；
- 没有重复已有成熟工具或工作流；
- `SKILL.md` 中每条指令都能解释它会在什么条件下改变行为；
- supporting references 都有明确读取条件；
- examples 与 instructions 不冲突；
- eval 没有只复用教学 examples；
- 新增脚本已实际验证；
- 修改已有 Skill 时没有破坏其调用者、作用域和已有权限边界。

优先通过 Git 保留修改历史。提交说明应准确描述这次改变的是 Skill 指导、reference、example、eval 还是项目知识，不夸大验证程度。
