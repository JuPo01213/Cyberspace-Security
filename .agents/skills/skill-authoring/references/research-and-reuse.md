# 成熟工作流调研、来源与复用

本参考用于创建或修改 Skill 时判断：什么时候应该搜索成熟方案、怎样判断来源、怎样避免把拼装方案冒充成熟实践。

## 默认倾向

如果问题已经存在成熟生态、官方工具、标准工作流、广泛使用的框架或专门 Skill，先调查它们，再决定是否自建。

尤其在以下情况主动搜索：

- 用户明确要求成熟工作流、官方方法或社区实践；
- 当前方案需要大量手写基础设施；
- 已知有主流工具或框架；
- 当前失败可能来自不了解现有能力；
- Skill 正在规定一个本领域已有惯例的流程。

不是所有小改动都需要重新调研。已经有当前、可信且与任务完全匹配的来源时，可以复用，不为形式重复搜索。

## 来源分层

### upstream_official

上游项目、官方文档、正式规范、官方仓库。

可用于确认：

- 工具真实能力；
- 参数与接口语义；
- 官方支持路径；
- 当前推荐用法。

官方示例只证明“这是合法/支持的用法”，不自动证明它是当前项目最优路径。

### curated_secondary

Skill reference、博客、教程、团队整理、社区手册、二次汇总。

可用于：

- 快速建立地图；
- 发现候选方法；
- 收集实践经验。

不要把它称为上游官方，也不要用它单独证明官方行为。

### project_evidence

当前项目自己的：

- 运行记录；
- problem slices；
- benchmark；
- fixture；
- bug report；
- commit / PR；
- 用户确认。

它最能说明“当前项目实际上发生了什么”，但未必能推广到其他项目。

### local_observation

当前任务或当前机器上的直接观察。

它对当前状态最有价值，但通常覆盖范围最窄。

## 调研后的结论必须标清性质

至少区分：

- 官方明确要求；
- 官方支持但不强制；
- 社区常见实践；
- 当前仓库已验证实践；
- 基于多来源综合得到的工程建议；
- 尚待验证的假设。

不要把最后三类写成“官方标准”或“久经考验”。

## 复用成熟方法时仍要验证适配

不要机械抄上游流程。

检查：

- 当前版本是否一致；
- 当前平台是否一致；
- 当前任务目标是否一致；
- 当前权限和网络边界是否一致；
- 官方示例是否覆盖当前输入结构；
- 本地已有证据是否已经满足某些前置条件；
- 引入该方法是否建立第二套状态机或重复已有权威。

成熟工具优先，不代表成熟工具永远正确；任务事实与可验证后置条件仍然是最终落点。

## 缺工具时先解决工具

当任务真正依赖某项成熟能力，而环境中没有它时：

1. 确认该能力确实必要；
2. 优先安装、配置、连接或修复成熟方案；
3. 验证消费者能够实际使用；
4. 只有成熟方案存在明确不可复用缺口时，才做最小 adapter；
5. 不因为安装麻烦就转去手写一个低质量替代物。

但也不要把“安装完整工具栈”变成所有任务的固定前置；只建立当前任务真正依赖的能力。
