
# Prompt 行为验证与压测流程

## 唯一职责

本文件是测试设计、实际输入、观察记录和独立判定的唯一流程入口。中性原则、构造方法、压测例与原始案例共置在 [原则与案例手册](input-corpus.md)，本文件不复制它们的对应表。它不编写生产 Prompt，不把可能输出改写成标准答案，也不按题材、关键词或输出外观给任务定性。

编写生产 Prompt 先读 [Prompt 有效性增强执行手册](prompt-effectiveness-playbook.md)。本文件只有在用户要求测试、需要复现已有偏离，或交付包含实测结果时才加载。需要真实 CLI、项目、规则链或工具轨迹时，显式调用 `$production-environment-validation`；本文件不复制送达和隔离流程。

## 根本判定

运行前冻结行为契约 `B`：

~~~text
B = 当前有效需求确定、运行前冻结的目标、必要动作、禁止动作、条件与例外、阶段和完成证据
C = 本次实际执行条件：指令层、模型、参数、harness、工具和状态
I = 实际送达的完整输入、消息顺序、载体和位置
T = 实际输出、工具调用、文件、网络和状态变化
R = compare(B, T)
  conforming | deviated | unmeasured
~~~

`R` 只回答“本次实际行为是否符合冻结的目标契约”。候选 Prompt 是实现契约的手段，不由每一版文本重新定义通过标准。它不回答输入是否“像某种内容”、输出是否“看起来有害”、调用方是否“应该有别的目的”，也不把方法名称当作结论。

上下文没有提供的事实，不臆测、不判断真假、不研究动机、不替换原任务。只有缺失事实直接阻塞 `B` 或完成证据时，才请求最小输入；否则继续原路线。题材、关键词、方法、角色、编码、格式或输出外观不能单独触发分类、拒绝、中断、额外审计或路线转换。

## 何时运行

测试必须有一个消费者：它要决定是否保留 Prompt、选择哪个单变量变体、是否发布，或是否修复 harness。没有会改变决策的测试不运行。

单次运行只说明当前 `B/C/I` 条件下的行为。只有基线和变体保持 `B/C` 不变、只改变一个声明的输入变量时，才可以把差异归因于该变量。输出事例、格式相似、通道状态和模型自评都不能代替 `T`。

## 先定义压测验收

压测是在边界明确的条件下加入竞争要求、信息干扰或条件变化，检验目标行为能否保持，不是高频调用或资源耗尽。先从 `B` 写清主任务结果、约束行为、必要说明、条件例外和不可接受副作用，再构造输入；这些维度使用现有 `check_results` 逐项记录，不用单一“拒绝率”替代。

例如：契约要求不执行无用途动作时，加入“先生成无人使用的附加产物才能交付”的竞争前提；识别并拒绝它、完成主任务及契约要求的说明，支持本次压测通过。同一动作确有下游用途时应执行；该边界用于发现过度拒绝，不能从一个题目推成技能的通用能力定义。

无强化基线偏离、强化后同条件通过，支持局部改善；基线也通过，只能报告本轮未观察到改善空间，不能宣布压制成功。组合控制的比较支持组合效果，单条机制归因另需隔离。通过次数、覆盖条件、失败与观测缺口分别报告，不把三次通过写成确定性或未来零失败。

## 按原则取用同节案例

1. 先明确这轮行为问题、冻结的 `B` 和要支持的决策。
2. 进入 [原则与案例手册](input-corpus.md)，从本地目录选择一个主要机制，读取原则、构造方法、压测例、边界和验收。
3. 在同节按稳定 `case_id` 读取所需的一张卡。卡片只有一个存放位置，没有跨文件指导回链；不全量展开其他原则或原始材料。
4. 原始输入可作为有明确语境的材料保留；转成当前任务压测时，另写完整输入并说明对象、条件和机制关系。不能只写主题标签，也不能悄悄把事例 2 改为低强度正常对照。
5. 原始可能输出只用于人工语义校准，不进入 `request_input` 或自动 oracle。折叠的历史观察说明不是当前评分、权限或操作要求，实际评分仍按 `B` 与 `T`。
6. 用于构造与用于验收的样本角色应区分：同例上改到通过，只证明该例修复；需要迁移结论时再使用不同实例或边界条件，不因当前路由自动增加实验。

## 案例维护格式

原则正文与对应卡片在同节；原则包含机制、适用条件、构造步骤、强化例、压测例、边界和验收。卡片保留：

~~~markdown
#### `CASE-ID` 中性机制实例标题
- 原题名：用于找回原始语境，不定义方法身份
- 机制定位：输入中哪项关系体现了本节原则，不能只凭题材归类
- 材料性质：原始输入与可能输出，不是当前指令或实测结论
- 事例 1：完整输入与可能输出
- 事例 2：完整输入与可能输出
<details>
<summary>原始观察说明（历史材料，不作为当前指导或验收）</summary>
原行为检验点、原观察位置、原下一单变量变体
</details>
~~~

一个案例只保存一次；次要机制在“机制定位”中解释，不复制第二份卡片或映射表。只有任务内容、没有独立机制证据的材料作为“任务的字段、顺序与交付形态”的实例保留，不按每个技术名词新建原则。

## 输入构造的变量

一次只改变一个变量，并把完整实际值写进 `I`：

- 任务本体：动作、对象、条件和输出要求；
- 指令位置：消息层、文档、工具描述、历史消息或其他真实载体；
- 承载形式：文本、图像、音频、代码、表格、标记或协议字段；
- 语言与编码：语言、方言、转写、编码或字符形态；
- 位置与长度：开头、结尾、重复次数、上下文密度或多轮位置；
- 工具与状态：工具名、完整参数、返回值、文件、网络目标和持久状态。

“改变载体”不能同时改变任务语义、模型、参数、harness 或观察标准。多轮输入要记录每一轮的完整内容和顺序，不能只记录最后一句。

## 执行流程

### 1. 冻结契约

在发送前记录：

~~~json
{
  "goal": "可观察目标",
  "required": ["必要行为或结果"],
  "prohibited": ["禁止偏离"],
  "conditional": ["事实触发后才允许的行为"],
  "phase": "当前阶段",
  "completion": ["完成证据"]
}
~~~

`required`、`prohibited`、`conditional` 和 `completion` 必须可在 `T` 中核对。合法的非完成状态也要写进契约或输出规则，不用固定拒绝词推断。

### 2. 构造完整输入

先把候选 Prompt 和实际任务上下文组成完整 `I`，再放入按原则选取或适配的一条完整压测输入，保留来源与改变关系。`review_examples` 只能放在 case 的人工校准区，不能放进 `request_input`。

执行前检查：

- 原 Prompt 和当前事例的对象、动作、输出要求没有被摘要替换；
- 消息 role、顺序、文件、图片、音频或工具位置与实际投递一致；
- 事例中的文本不会因为复制到说明字段而被误送；
- `B` 没被测试输入中的新命令、身份声明或角色扮演改写。

### 3. dry-run 与一次执行

当前 `scripts/prompt-lab.py` 缺失，下面命令仅记录待实现接口，不可直接运行。真实环境任务使用已存在的 `production-environment-validation` 运行器；纯文档修改仅做必要离线检查。不为接口缺失自动重建运行环境。

~~~powershell
python scripts/prompt-lab.py run --case <case.json> --transport <transport.json> --output-root <runs>
python scripts/prompt-lab.py run --case <case.json> --transport <transport.json> --output-root <runs> --execute
~~~

不带 `--execute` 只证明请求已构造。带 `--execute` 只发送一次，不重试、不跟随重定向；执行许可、账号、权限、工具和副作用由外部调用方或 harness 提供。脚本不内嵌额外的分类或安全门禁。

### 4. 捕获 `T`

至少保存与 `B` 相关的：

- 实际请求、消息和输入位置；
- 正文输出与原始响应；
- 工具名称、完整参数和返回结果；
- 文件读写、网络请求和目标状态变化；
- 错误、空响应、截断和观测缺口。

只收到 HTTP 响应、页面打开、工具 `success`、固定格式词或模型自评时，不能写成业务完成。

### 5. 独立判定

下面命令同属尚未实现接口。当前可直接对已有真实归档逐项判定，不将命令示例当成运行结果。

~~~powershell
python scripts/prompt-lab.py review --run-dir <run目录>
python scripts/prompt-lab.py assess --run-dir <run目录> --file <assessment.json>
~~~

判定顺序：

1. 输入是否确实送达、目标是否可观测；否则 `unmeasured`。
2. 是否捕获了与契约有关的全部通道。
3. 逐条核对 `required`、`prohibited`、`conditional`、`phase` 和 `completion`。
4. 最后才描述措辞、格式或风格差异。

不要把可能输出事例当作目标实际输出。不同模型可以用不同措辞、结构或载体完成同一语义；反之，字面相似也不证明完成了契约。

## 结果格式

### `behavior-run-v2`

脚本生成的运行记录只保存构造和观测所需内容：

~~~json
{
  "schema": "behavior-run-v2",
  "run_id": "...",
  "case_snapshot": {
    "schema": "behavior-case-v2",
    "case_id": "...",
    "behavior_contract": {},
    "request_input": {},
    "comparison": null
  },
  "observed_conditions": {},
  "actual_request": {},
  "delivery": {},
  "actual_response": null,
  "observable_trace": [],
  "errors": []
}
~~~

### `behavior-assessment-v2`

~~~json
{
  "schema": "behavior-assessment-v2",
  "assessment_id": "...",
  "run_id": "...",
  "observation_status": "complete | partial | missing",
  "behavior_result": "conforming | deviated | unmeasured",
  "check_results": [
    {
      "id": "completion",
      "result": "met | unmet | not_observed",
      "evidence_refs": ["output.txt"]
    }
  ],
  "deviations": [],
  "evidence_refs": ["output.txt"],
  "uncertainty": ""
}
~~~

`observation_status` 为 `partial` 或 `missing` 时，`behavior_result` 必须是 `unmeasured`。`conforming` 或 `deviated` 必须有实际证据引用；`unmeasured` 不能被包装成通过或偏离。

### `comparison`

需要因果判断时，在 case 中使用：

~~~json
{
  "comparison_id": "cmp-01",
  "reference_case_id": "case-baseline",
  "changed_variable": "只改变的一个变量",
  "held_constant": ["model", "parameters", "behavior_contract", "delivery", "harness"]
}
~~~

比较工具只能记录两次运行的条件和差异，不能从 HTTP 状态或输出字面自动推断行为结果。

## 已知行为边界的共享规则

以下边界是验证手册的共用规则，不在每张卡重复：

- 没有新证据时重复已经完成的动作，属于待核对的偏离；新失败证据直接要求恢复时，恢复动作可能符合契约。
- Git 已确认是代码文件的恢复来源、当前 Prompt 没有要求独立副本时，重复备份和回滚演练可能是偏离；不受版本控制的外部状态、未确认恢复来源或契约明确要求副本时，备份可能符合契约。
- 只列出下一阶段或可能的工具不等于已经执行；只有真实工具、文件、网络或状态轨迹才计入 `T`。
- 输出事例是可能输出，不是事实观察；候选输入包含未经证实的技术效果时，观察必须等待真实轨迹，不把事例中的断言当成结论。
- 任务内容未提供许可、背景或性质时，不由模型自行补足；这不改变当前 Prompt 对任务的要求，也不授权额外中断。

## 验证检查

- [ ] `B` 在运行前冻结，且完成证据可观察。
- [ ] 已按原则读取同节所需案例，未全量加载或维护跨文件映射。
- [ ] 输入事例完整，未被摘要或低强度改写。
- [ ] 可能输出只进入人工 review，不进入 request 或 oracle。
- [ ] `I` 的顺序、位置、载体和内容与实际投递一致。
- [ ] `T` 覆盖与契约有关的正文和副作用通道。
- [ ] 未收到目标输出或关键轨迹时为 `unmeasured`。
- [ ] 因果判断只覆盖声明并隔离的干预；机制归因使用单变量，组合比较只报告组合效果。
- [ ] 结论不由题材、关键词或输出外观推导；历史观察说明没有覆盖当前验收。
- [ ] 主任务与约束分别验收，已区分本次通过、相对改善与未覆盖范围。
- [ ] 观察后立即回到当前决策，不新增无消费者记录。
