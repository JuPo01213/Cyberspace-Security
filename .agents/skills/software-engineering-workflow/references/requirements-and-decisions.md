# 持续需求发现与决策

需求不是项目开始时填写一次的表格，而是开发过程中不断收敛、可追溯的“已确认产品行为”。

## Invariant：发现不等于决定

以下都可能暴露需求：用户原话、现有行为、Research、Prototype、Design、Implementation、Review、Acceptance。

它们只是证据来源。只有被明确确认、或由无需价值判断的事实直接确定的内容，才能成为稳定 Requirement。

## 不要让专业化表达覆盖原始意图

需求结构化是有损压缩。模型可以抽象，但必须保留来源关系：

`用户原话 → 当前解释 → 已确认行为 → 工程映射`

禁止把：

> “我希望简单一点，打开图片马上能改。”

直接压成：

> “需求：单文档架构。”

“单文档”是可能的工程/产品解释，不是用户原话本身。

## 三类未知 + 一类历史不确定

### 事实未知
→ Research。

### 设计未知
→ Design / Prototype。

### 价值未知
→ 用户决策。

### 历史意图未知
当前只剩摘要、术语或旧 Spec，无法确定用户当时真正表达了什么。

→ Requirement Provenance / Source Recovery。

## Assumption-first，而不是 Question-first

用户不应从零完成模型能够完成的判断。

Agent 先：
- 读代码和文档；
- 查事实；
- 根据项目规模和已知偏好形成推荐；
- 识别哪些部分仍需要用户价值判断。

然后把产品决策以“推荐默认 + 例外纠偏”的形式交给用户。

## Deep Mapping 的边界

用户说出的名词未必等于真正需求，例如“文件管理器”“考勤系统”“记账本”。Agent 应追到真实动作、痛点、统计/状态/边界等结构。

但 Deep Mapping 不能变成：

> “我比用户更懂他，所以我决定他其实不需要软件。”

如果用户明确在寻求代码制品，深层映射的目标是确定**正确的软件行为、规模和入口**，而不是用手工办法替代其开发意图。

## Adaptive Probing

不要固定问一套问题。

只有出现以下信号时才追加探针：
- 用户表述低置信度；
- 前后回答冲突；
- 同一个词可能有多种口径；
- 多角色需求明显不同；
- 外部合规/组织压力可能决定行为；
- 需求稳定度影响架构；
- 实现已经形成未定义行为；
- 现有框架明显解释不了当前案例。

可以按需采用：场景化、负向边界、基线对比、失败终局、反例、自我对抗、粗原型等方法。它们是工具，不是固定仪式。

## Requirement State

建议状态：
- **Confirmed**：已确认；
- **Assumed**：暂时假设，可继续低风险可逆工作，但不能伪装成确认；
- **Open Decision**：待决；
- **Uncertain**：用户明确选择“不确定”；
- **Rejected / Non-goal**：明确不做；
- **Superseded**：被后续决策替代。

每个高影响 Requirement/Decision 尽量保留：
- source_ref / raw_excerpt；
- 当前自然语言行为；
- scope；
- status；
- supersedes / invalidated_when；
- code/design evidence。

详见 `semantic-integrity.md`。

## 从代码反推需求

代码不是需求权威，但它是发现隐含产品决定的强证据。

Procedure：
1. 先独立观察代码/运行结果；
2. 重建 Behavior Snapshot；
3. 再和 Requirement 对照；
4. 找出新增、缺失、变化、无法确定的行为；
5. 将真正需要用户判断的差异进入问卷；
6. 用户提交后更新 Requirement；
7. 必要时返回 Design / Implement。

这样可以降低“拿着 Spec 看代码，所以什么都觉得符合”的确认偏差。

## Gate

如果未决项会改变关键用户行为，则阻止继续固化或 Finish。

内部实现细节通常不触发用户决策，例如 Map/Object、私有函数拆法、内部缓存容器。
