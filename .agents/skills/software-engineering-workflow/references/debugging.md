# 系统调试

Debugging 的核心纪律：**没有反馈回路，不开始修。**

## 1. Reproduce

先得到一个稳定失败：
- 一个测试；
- 一个最小命令；
- 一个 HTTP 请求；
- 一个 UI 操作序列；
- 一个 benchmark。

失败必须真的对应用户问题，而不是“看起来相关”的错误。

## 2. Minimize

减少变量：
- 最小输入；
- 最小数据；
- 最少依赖；
- 去掉无关服务；
- 找到最短重现路径。

目的不是漂亮，而是让原因空间变小。

## 3. Hypothesize

一次提出少量可证伪假设：

```text
如果 X 是原因，那么观察 Y 应该出现；
如果 X 不是原因，Y 应该不会出现。
```

不要一边改五个地方一边“看看会不会好”。

## 4. Instrument

增加最小必要观测：
- 日志；
- tracing；
- counters；
- SQL；
- profiler；
- debugger；
- bisect。

观测必须区分假设，不是为了“收集更多信息”。

## 5. Fix

找到根因后：
- 先写 regression test 或等价失败证据；
- 修根因；
- 不只隐藏症状；
- 不顺手大重构。

## 6. Regression

运行：
- 原复现；
- 新 regression test；
- 相邻行为；
- 必要全量测试。

若根因暴露“没有良好 seam”，把架构问题单独记录并进入设计/重构流程，不在 Bug fix 中无限扩张。

## 性能问题

性能调试必须有测量：
- baseline；
- profile；
- 目标指标；
- 改动后测量；
- 正确性回归。

不要凭直觉优化。
