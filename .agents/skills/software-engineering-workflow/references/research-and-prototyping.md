# 调研与原型

Research 和 Prototype 解决不同类型的不确定性，不要混用。

## Research：解决事实问题

适合：
- 外部 API、协议、框架行为；
- 当前版本的官方限制；
- 安全/兼容性规范；
- 依赖维护状态；
- 第三方系统真实能力。

工作方式：
1. 先写清问题和需要决定什么；
2. 优先官方文档、源码、规范、一手 issue/release；
3. 社区资料用于补充经验，不覆盖一手事实；
4. 记录版本、日期和适用条件；
5. 输出“结论 → 证据 → 对设计的影响”。

不要为了“全面”做无限检索。只搜到足以改变当前决策。

## Prototype：解决设计问题

Prototype 应回答一个明确问题，例如：
- 这个交互是否容易理解？
- 两个状态模型哪个更简单？
- 性能是否足够？
- 一个 seam 是否真的可测试？
- SDK 的真实调用体验如何？

要求：
- 代码可丢弃；
- 尽量隔离，不污染生产结构；
- 不做生产级抽象、迁移、兼容层；
- 预先定义成功/失败判据；
- 结束后保存结论，决定“采纳 / 否决 / 继续实验”。

## 什么时候不能直接把 prototype 变成生产代码

出现以下任一项时，重新按 Design + Plan 实现：
- prototype 绕过了真实错误处理；
- 使用硬编码/假数据；
- 缺少权限或数据边界；
- 结构是为了快速实验而不是长期维护；
- 没有测试 seam；
- 依赖版本、接口或架构只是临时选择。

Prototype 的最重要产物是决策证据。
