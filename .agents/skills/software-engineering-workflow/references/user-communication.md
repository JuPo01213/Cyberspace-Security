# 用户沟通

沟通不是包装层，而是工程控制面。

默认假设：**用户完全不懂开发。**

## 两个预算

### Attention Budget

控制“应该打扰用户多少次”。

用户的注意力是稀缺资源。频繁低价值确认会形成确认疲劳，最终让“确认”失去意义。

因此：
- Agent 先研究和判断；
- 独立决策批量展示；
- 推荐作为默认值；
- 用户只处理例外；
- 低影响内部决策不打扰用户。

### Cognitive Load Budget

控制“每次打扰要求用户理解多少东西”。

不得以用户尚未建立的技术知识作为下一项决策的前置条件。若解释开始依赖一串陌生术语，应退回用户场景和可观察结果。

## Invariant：产品决策用用户语言表达

技术实现先转换：

`实现细节 → 实际行为 → 使用场景 → 用户可感知差异 → 推荐默认 → 用户纠偏`

不要问：

> “你需要 optimistic update 吗？”

改为：

> “你点保存后，我默认让界面立刻显示成功；如果后台失败再恢复。这样响应更快。如果你更希望等服务器确认后再显示保存成功，可以改成后者。”

## 设计对齐：需求已明确，不等于方案已对齐

当设计会改变用户的使用流程、默认结果、数据去向或重要取舍时，进入 Plan / 实施前先把**拟议方案**讲成用户能判断的实际过程：用户做什么，系统接着做什么，用户看到或得到什么；发生冲突、失败或判断不稳时会怎样。用一个贴近当前任务的例子走通正常情况，再说明一个会影响选择的边界情况。区分用户已确认的目标、代理建议的实现方式和尚未验证的效果。

解释应让用户能指出“这里不是我要的”，无需读懂代码或替代理设计内部结构。例如面对“快速保存笔记”，先说明笔记会放在哪里、理解内容何时写入、保存完成后能否立刻找到；不要只列出缓存、队列、索引等实现名词。

只把真正会改变使用体验的取舍交给用户。代理应先给出推荐及理由，再用一个简短的问题或可纠正的场景取得对齐。用户表示没看懂时，缩小到一次具体操作，换用示例、前后对比或小图解释；这不是同意方案的信号。用户指出不符合预期时，先修正设计并重新展示受影响的行为。沉默、表达需求、认可问题存在，都不等于认可代理方案。

设计对齐不是每个内部实现细节的审批。用户已经明确指定的行为无需重复确认；行为不变的局部重构可简要说明后继续。只有关键用户行为或取舍仍未被理解和校准时，才暂停依赖该决定的实施。

### 对齐时的具体说法

当方案会改变架构、性能、后台运行时间、GPU/内存占用、保存位置或数据去向时，不要只报“我建议缓存/常驻/异步”。先用一段普通语言说明：

- **现在发生什么**：说用户当前做的动作和系统实际做的事；把代码直接证明的事实与尚未测量的影响分开。
- **采用方案后会怎样**：按一次具体使用过程讲清第一次、后续重复使用、失败时分别发生什么。
- **代价什么时候出现、什么时候结束**：例如资源从哪个动作开始占用，哪一个可观察事件会释放；如果宿主何时关闭后台服务尚未确认，明确说“我还没有确认它什么时候会关闭”，不要把“应用开着”当作证据。
- **推荐与取舍**：说清用户会获得什么、需要承担什么，以及你推荐哪种方案和理由。

可以按这个句式组织，但用词要贴合当前产品：

> “我确认现在每次保存都会……；它可能造成……，但实际耗时还没测过。建议改成……。这样你第一次……，之后……；代价是……一直保留到……。我推荐它是因为……。这个过程和代价符合你的预期吗？”

避免要求用户在“cache、worker、singleton、process lifetime”等术语间做选择。需要保留术语时，先给出上述实际过程，再把术语作为括号里的简称。不要问“你听懂了吗”；用户如果说没看懂，就用更短的一次操作示例重新说明，不把解释责任推给用户，也不继续实施依赖该设计的代码。

## 默认不是逐项批准

如果模型大多数时候已经能给出合理推荐，就不应要求用户机械地点“同意”。

默认交互：
- 推荐选项预选；
- 用户不修改 → 接受推荐；
- 改选/填写 → 覆盖推荐；
- 选择“不确定” → 保持 unresolved。

这和权限审批一样：如果每一步都要求手动批准，用户会形成机械点击习惯，反而降低真正重要事项的敏感度。

## 批量而不是连环追问

多个相互独立的问题进入同一轮问卷；只有依赖前一答案的问题进入下一轮。

不要追求“一次把所有未来问题问完”，也不要一题一轮。

详见 `decision-questionnaire.md`。

## Progressive Vocabulary

共享词汇用于减少重复解释，但不能强迫用户学习术语。

建议节奏：
1. 第一次：完整自然语言场景；
2. 第二次：场景 + 一个短名称；
3. 用户已自然理解后：可直接使用短名称；
4. 一旦出现困惑：立即退回场景。

专业术语只在内部工程层使用，除非用户本身已经使用并理解它。

## 不把技术工作推回用户

提问前先：
- 看代码；
- 查项目文档；
- 调研事实；
- 做必要 prototype；
- 构造推荐方案。

事实是 Agent 的责任，产品价值判断才是用户的责任。

## 行为走查比抽象提问更高带宽

与其问：

> “你还有哪些 edge case？”

不如描述当前真实行为：

> “现在你打开图片 → 编辑 → 导出。如果同名文件存在会直接覆盖；关闭未导出的编辑时不会提醒。”

然后让用户纠偏。

## 原型也是沟通媒介

对于“像某个产品”“感觉不对”“视觉/交互说不清”的低带宽需求，不强迫用户继续用语言描述。先做低成本、可丢弃原型，让用户指出“哪里不像/哪里不对”。

## Gate

如果用户必须先学会一套技术知识才能回答当前产品问题，则沟通尚未完成。
