# 验收、行为走查与需求回流

Acceptance 不是单向终点。

它有两个目的：

1. 证明已确认需求已经实现；
2. 从真实使用路径发现此前没有定义的需求。

## 第一部分：Requirement → Evidence

对复杂任务建立：

```text
需求 A → 测试/观察 A
需求 B → 测试/观察 B
约束 C → 回归/静态检查 C
```

没有证据的需求仍是“未验证”。

## 工具成功 ≠ 业务成功

区分：
- 命令成功；
- 文件写入成功；
- HTTP 200；
- 测试退出 0；
- 业务后置条件成立。

## Behavior Reconstruction

对于语义风险较高的改动，先从当前产品独立生成 Behavior Snapshot，再与 Requirement 对照。不要只拿验收标准逐条找证据而忽略实现额外产生的行为。

## 第二部分：Behavior Walkthrough

按真实用户路径描述当前系统：

> 用户从开始到完成会经历什么？

尽量使用自然语言，而不是代码和内部状态名。

重点走查：
- 第一次使用；
- 空状态；
- 重复操作；
- 失败；
- 取消；
- 关闭；
- 未保存；
- 冲突；
- 覆盖；
- 权限不足；
- 多对象/多账号；
- 网络中断；
- 恢复。

目的不是“多测几个 edge case”，而是发现：

> 现在的代码是否已经替用户做了一个之前没确认的产品决定？

## Requirement Gap

如果 walkthrough 暴露：

- 用户可感知行为未被需求定义；
- 实现和用户预期可能不同；
- 两种合理行为都存在；

则：

1. 不把它静默判为通过；
2. 不由 Agent 自己选一个“更好”的体验；
3. 将当前行为翻译为用户场景；
4. 若有多个独立差异，合并成带默认推荐的 Decision Questionnaire；
5. 用户一次提交后更新 Requirement；
6. 必要时返回 Design / Implement；
7. 重新验收。

## 验证强度

### 低风险局部改动
- 目标测试；
- typecheck；
- diff review。

### 中等功能
- unit/integration；
- 相关回归；
- 关键 UI/API smoke；
- build；
- 行为 walkthrough。

### 高风险变更
- migration dry-run；
- rollback/recovery；
- 数据一致性；
- staging / canary；
- 观测指标；
- 明确人工验收。

## 边界验证

修复一个方向时验证反向边界。

例如：
- 低风险任务不过度验证；
- 高风险迁移仍做必要校验。

## Gate

进入 Finish 前必须满足：
- 已确认需求有最新证据；
- 关键 walkthrough 已完成；
- 没有未处理的关键 Requirement Gap；
- 未验证项已明确标记。

## 最终验收摘要

```text
已确认行为：
- …

验证：
- `command` → PASS
- 场景走查 … → PASS

新发现并已确认：
- …

未验证/限制：
- …
```


## 结构验收

对重构或设计调整，验收不仅看新行为是否工作，也检查旧结构是否真正退出。

如果没有真实兼容约束，验收应确认：
- 旧接口已删除；
- 旧调用方已迁移；
- legacy fallback 不再存在；
- 双写/双读已收敛；
- 没有无消费者的 adapter；
- 同一概念只剩一个权威表示。

“新代码能跑，但旧代码也暂时留着”不算重构完成。
