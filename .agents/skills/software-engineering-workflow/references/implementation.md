# 实现

实现阶段把已确认的 Requirement、Design、Plan 变成代码。

## Invariant：实现不得静默发明产品行为

实现者可以自主决定内部技术细节。

但如果实现过程中出现当前需求未定义、且用户能感知的行为，必须暂停固化并进入 Requirement Discovery。

典型信号：
- 自动覆盖还是询问；
- 关闭是否保存；
- 默认排序；
- 失败是否重试；
- 是否支持多个对象；
- 空状态如何表现；
- 权限不足如何提示；
- 数据保存在本地还是远端。

## 每个切片开始前

读取：
- 当前 task；
- Requirement；
- Design seam；
- 文件范围；
- 验证命令。

若核心假设错误，返回上游，不偷偷改目标。

## TDD：默认生产行为模式

适用于稳定可描述的生产行为：

`RED → GREEN → REFACTOR`

1. 写目标行为失败测试；
2. 确认失败原因正确；
3. 写最小实现；
4. 使测试通过；
5. 重构；
6. 运行相关验证。

Prototype、文档、一次性探索不机械要求 test-first。

## 实现中 Requirement Check

每完成一个垂直切片，问：

> 这个切片是否让用户看到或经历 Spec 未定义的新行为？

如果“是”：
- 不继续把它扩散到更多代码；
- 将行为翻译为用户场景；
- 进入 Requirement Discovery；
- 用户确认后继续。

## 实现纪律

- 复用项目 pattern；
- 不新增未使用依赖；
- 不顺手重构无关区域；
- 错误处理对应真实失败；
- side effects 集中；
- 边界数据在边界处校验；
- 注释解释 why。

## 并行 / Subagent

下发：
- task；
- 必要 Requirement；
- Design；
- 文件范围；
- 验证要求。

不要无筛选传整个历史。

主 Agent 负责整合、Requirement Gap 收集和最终验收。


## 不以补丁代替重构

当实现过程中确认当前结构本身错误时：

- 不继续在错误 seam 上添加条件分支；
- 不为了避免修改调用方而堆 wrapper；
- 不长期保留旧接口和新接口并行；
- 不把临时 migration code 变成永久主路径。

如果不存在真实兼容约束，直接更新依赖方并删除旧结构。

### 删除也是实现的一部分

完成新结构后，主动删除：
- 被替代接口；
- dead code；
- 旧 feature flag；
- legacy fallback；
- 无消费者 adapter；
- 已完成迁移的双写/双读逻辑；
- 仅为过渡存在的测试。

不要把“现在能跑”当作保留旧路径的理由。

## Convergence 与状态晋升

重要垂直切片跑通后，必要时从真实代码/运行结果形成 Behavior Snapshot。不要仅根据“计划写了什么”判断实现语义。

实现过程中发现稳定、会长期影响后续开发的新事实时，先作为 Candidate State Update；只有有来源、scope 和稳定性证据后才晋升 Project State。
