# Skill Packaging

把 Skill 当作可执行的操作手册来设计和维护：它必须改变模型在具体任务中的行为，并让关键行为可以检查；不要把它写成研究报告、概念介绍或原则清单。

## 全局执行原则

在整个创建、审查、验证和演进过程中，始终**从第一性原理、整体性地去对抗性审查**：

- **第一性原理**：从要解决的问题、目标行为、必要条件和因果关系推导规则；不因惯例、既有写法或模型常识而默认某个方案正确。
- **整体性**：同时检查规则之间、文件之间、切片与主规则之间、依赖与运行结果之间的关系，以及修改带来的连锁影响；不要只优化局部段落。
- **对抗性审查**：主动寻找反例、边界条件、隐含假设、冲突、遗漏、误用路径和回归风险；尝试证伪当前方案，而不只是证明它看起来合理。

这三项是贯穿全流程的工作方式，不是需要机械重复的目录章节或检查项。

## 1. 先定义任务与成功标准

创建或修改 Skill 前，先明确：

1. **问题**：什么重复出现的真实问题需要被解决？现有行为具体在哪里失败？
2. **目标行为**：模型遇到哪些输入或情境时，应执行哪些动作、作出哪些决策？
3. **成功标准**：观察什么结果，才能判断 Skill 确实起作用？
4. **适用边界**：哪些情况适用、不适用，哪些条件会改变处理路径？
5. **证据与未知项**：哪些结论来自实际案例或验证，哪些仍是推断、假设或待验证判断？

不要在问题和目标尚不清楚时，先堆积原则、模板或章节。

## 2. 把规则写成可执行的行为

每条重要规则都要能回答：**模型何时行动、执行什么、依据什么作出选择、怎样确认结果正确。**

- 将“充分考虑”“合理处理”“全面审查”等抽象要求，改写成具体动作、触发条件、决策标准和验证方式。
- 优先使用可观察的行为描述。例如，不只要求“检查引用”，还要明确检查目标文件是否存在、引用是否准确、加载路径是否可用。
- 对不可妥协的要求使用“必须”“不得”；对条件触发的动作明确触发条件；对允许权衡的事项保留判断空间。
- 祈使句数量不是质量指标。指令只有落到具体行为、决策或可验证结果上，才算有效。
- 解释只用于消除真实歧义、说明约定、界定条件、解释必要原因或记录例外；不要用大段背景知识替代操作步骤。
- 不要假设模型会自动把抽象原则转化为正确行为。关键要求必须给出足够明确的执行落点。

## 3. 控制上下文成本，而不是盲目缩短

默认模型已经知道一般概念和常见方法。不要把 Skill 写成基础教程；保留那些会改变决策或避免错误的专用信息。

优先保留：
- 项目或任务专属的约定；
- 容易混淆、具有多重含义的术语；
- 适用条件、边界、例外与失败处理；
- 决策标准、验证方式和不可违反的约束；
- 仅凭常识无法可靠推断的经验。

只有在删去内容后，仍不会增加歧义、错误决策、返工或遗漏风险时，才应删除。简短不是独立目标，减少重复和无效负担才是目标。

约 500 行是主文件需要复审的**触发线**，不是硬性上限，也不是要求到线就机械拆分。接近该规模时，评估内容职责、使用频率、常驻上下文收益、导航成本和规则一致性风险，再决定是否拆分。

## 4. 保持单一事实源，避免重复与引用迷宫

- 每条规则、术语定义和判断标准只保留一个权威定义；其他位置简短引用，不要换句话重复。
- 工作流步骤写该阶段需要执行的动作，不要在每一步重新解释全局原则。
- 检查清单检查结果是否成立，不要把正文逐条换写成另一份清单。
- `SKILL.md` 应足以支持正常执行。不得把关键约束拆散到多个文件，迫使模型通过多跳引用才能还原完整规则。
- 不要为拆分而拆分。引用文件只用于真正独立、低频、篇幅较长且按需加载有收益的内容；在主文件中直接说明何时需要读取它。
- 避免多层引用、相互引用和跨文件依赖网。渐进式披露的目标是减少无关上下文，而不是把完整规则拆碎、增加导航成本或造成遗漏。
- 长篇参考文件应提供清晰目录，并确认目标运行环境能够读取这些文件。
- 只有在宿主系统确实要求时，才增加额外文件或元数据；不要为形式完整而制造空文件。

## 5. 经验切片：从证据中抽象，不按对话机械切割

原始对话和案例是证据，不是最终结构。整理切片时：

1. 提取案例中的问题、上下文、实际动作、结果、失败原因、条件和例外。
2. 区分已确认事实、合理推断和待验证假设；不要把推测包装成事实。
3. 找出可复用的底层机制与适用边界，而不只复述个案经过。
4. 判断切片之间的关系：
   - 底层机制相同、边界一致且能够统一维护时，合并；
   - 单个案例包含多个可以独立复用的机制时，拆分；
   - 机制或适用边界不同，即使表面相似，也应分别保留；
   - 已有切片出现重复、错误或过时内容时，直接重写、合并、拆分或重组。
5. 只有当经验具有复用价值、证据足够且适用边界明确时，才将其提升为通用规则。单个案例不自动等于通用规则。

切片数量和原始对话的段落数都不是目标。以独立复用价值、机制清晰度、边界明确度和长期维护成本决定组织方式。不要为了保留原始措辞而牺牲准确性；可以自由重写和抽象，但不得丢失会改变结论的证据、条件、例外或关键区别。

## 6. 明确文件职责与演进边界

根据实际需要组织文件，避免没有价值的结构：

- **`SKILL.md`**：当前有效的操作规则、决策标准、工作流和验证要求；正常执行所需的核心内容放在这里。
- **`slices/`**：经过分析的经验切片与证据，供规则演进时追溯；不是原始对话的机械存档，也不是所有切片都必须加载的运行手册。
- **`references/`**：真正低频、独立、篇幅较长的补充材料；必须由主文件直接说明触发读取的条件。
- **Git 历史**：记录规则如何演进、为何改变及何时被替代；不要用 `v2`、`final`、`backup` 等并行文件代替版本管理。

优先让 Skill 成为边界清晰、可独立理解、可独立演进的最小维护单元。若宿主仓库已有统一的 Skills 组织约定，先检查并遵循该约定；不要未经评估就引入嵌套 Git 仓库、重复副本或另一套版本管理机制。若独立仓库是明确的项目约束，则应将整个 Skill 作为独立仓库维护，并把切片和参考材料纳入同一演进历史。

目录结构按实际内容调整，例如：

~~~text
skill-packaging/
├── SKILL.md
├── slices/
│   └── YYYY-MM-DD-topic.md
└── references/
    └── topic.md
~~~

不要为了匹配示例而创建空目录或占位文件。

## 7. 创建与维护工作流

### 阶段 A：恢复现状

- 读取现有 Skill、相关规则、文件结构和版本历史。
- 检查当前分支、已有改动、引用目标和外部依赖。
- 保留未提交改动；没有明确授权，不得覆盖或丢弃用户已有内容。
- 确认本次工作的目标、成功标准和真正尚未解决的问题。

### 阶段 B：分析证据

- 收集与目标直接相关的真实案例、失败样本、边界情况和验证结果。
- 区分事实、推断和假设。
- 按底层机制、适用条件和复用价值组织切片；根据需要合并、拆分或重写。

### 阶段 C：形成操作规则

- 从目标行为和必要条件推导规则。
- 为重要规则写清触发条件、动作、决策标准、失败处理和验证方法。
- 明确规则的适用边界与例外。
- 检查是否已有权威规则可复用；避免重复定义和跨文件拆散。

### 阶段 D：验证

根据变更风险选择验证深度，至少检查：

- **内容**：指令是否明确、可执行，是否存在含糊词、矛盾、遗漏或无依据的泛化。
- **结构**：文件职责是否清楚，是否存在重复规则、无效文件、引用迷宫或不必要的拆分。
- **行为**：对代表性正常案例、边界案例、反例和失败路径进行推演或实际测试，确认指令会导向预期动作。
- **回归**：检查修改是否破坏原本正确的行为、覆盖其他规则或改变不相关的决策。
- **引用与运行环境**：检查路径、文件名、元数据和加载方式是否真实存在且可用。

优先尝试推翻规则：构造会让规则失效的输入，检查相邻规则是否冲突，验证例外是否被遗漏。无法实际运行的测试必须标明未运行，不得把推演写成实际验证结果。

### 阶段 E：交付与记录

- 汇总实际修改的文件与规则变化。
- 报告执行过的验证、实际结果、未验证事项和已知限制。
- 只宣称有证据支持的完成状态。
- 如果本次没有实际修改文件，应明确说明；不要把建议或计划表述为已完成交付。

## 8. 持续演进

当出现新的可复用经验、反例、规则失效、边界变化、重复内容或维护成本上升时，评估是否需要更新 Skill。

先分类再修改：
- **个案**：仅记录为经验，不改变通用规则；
- **新增切片**：增加有独立复用价值的经验；
- **边界调整**：修正适用条件、例外或触发条件；
- **规则调整**：修改、替代或废弃当前操作规则；
- **重复合并**：合并同一机制的重复表达或切片。

修改前检查当前规则与 Git 历史，明确新证据改变了什么；修改后重新检查相关行为和回归风险。保留可追溯的演进历史，不以复制一份“新版”代替更新权威版本。

## 9. 完成前检查

交付前逐项确认：

- [ ] 问题、目标行为和成功标准明确。
- [ ] 重要规则已转化为具体动作、条件、决策或可验证结果。
- [ ] 已区分事实、推断与假设，并保留会改变结论的边界和例外。
- [ ] 规则有唯一权威定义，没有不必要的重复。
- [ ] `SKILL.md` 能支撑正常执行，引用直接、必要且可用。
- [ ] 切片按复用机制和边界组织，而非机械按对话切分。
- [ ] 已对反例、冲突、失败路径和回归风险进行审查。
- [ ] 实际验证与未执行的验证明确区分。
- [ ] 未覆盖或丢弃未经授权的既有内容。
- [ ] 交付说明准确列出修改、验证结果与限制。
