## 新取得的代码事实

在 Guest 中用 CDB 10.0.26100.9169 只读打开历史 `child_full_recv2.dmp`（SHA-256 `CA0FFCEC87A8580E9BFDEF4DAAF90C97FB06A53D597028020FE1EC714830E60D`）：

- `0x1407a443c..4448` 读取处理后的长度并比较 `0x37a`（890 字节），相等时跳至 `0x1407a4608`。
- `0x1407a4608..46b4` 将 `[rbp+0x70]` 开始的 890 字节复制到全局配置区 `0x141154980..0x141154cfa`（右端不含）。长度由六次 128 字节循环加 122 字节尾部得到；CDB 算式与宿主文本校验结果一致。
- 旧强推脚本修改的四个地址全部位于该配置区内：`ae7` 位于 `+0x167`；`ce9` 位于 `+0x369`；`ced` 位于 `+0x36d`；`cf1` 位于 `+0x371`。这些地址可由**通过指针整块复制**写入；旧 RIP-relative 扫描未找到直接写点，不表示没有自然写入路径。
- `ae7` 在已有代码中既被按首字节检查，又被取地址交给 CardLogin 候选函数。不能仅因 `cmp byte != 0` 就认定它是独立布尔授权标志。
- CLI 配置路径的局部字节也包含 `0x37a` 长度检查、整块复制和随后的 `StoredAuthorizationUsable` / `VerifyStoredCardStatusBeforeUse` 调用。它与“SDK 登录状态”不能合并成一个布尔量。

主产物：`runs/EPT-AUTH-LOCAL-20260926-19/offline.stdout.txt`，SHA-256 `E98BDD8F001500AFA49EAFA6C00316933EE180D1A83E07B57147CBC462A60103`。`listing-facts.json` 和 `verify_listing.py` 对 12 个关键指令字节、复制长度及字段范围做了文本校验。CDB 实际退出码为 0；前一离线读取（18）的退出码记录为 null，只能记未知。两次都不是样本运行。

## 限制与更正

1. 以上是历史快照中的代码，不证明该路径在当时执行，更不证明配置来自有效许可。完整原始样本到该历史 child 的同轮谱系也未在本轮重建。
2. 配置处理调用的参数形状包含 `0x208`、`0x660e`、16 字节材料和受保护包装；尚未闭合包装到实际加解密 API 的映射。C184 仅凭错误文案认定 BCrypt 的说法不能作为算法依据。本轮不导出密钥或构造配置。
3. 旧 `StoredVerify` 反编译在若干失败分支也返回 1；它是允许继续的策略结果，不等于完整许可状态。保存配置成功、字段检查成功、SDK 登录成功、目标解码成功必须分别证明。
4. C184 中“KEY 只作固定标识、不是授权凭证”没有充分依据：同一输入可以被多个消费者复用。原始外层字节码把 `card_key` 原样放入 `-k` 参数，也不能反向单独证明内部凭证语义。
5. C204 的“1029 是唯一剩余闸门”“完成设备侧派生即可解网络帧”“参考请求自洽即可视为合法自然响应”撤回为未证实推断。其十六进制字符限制、全部 writer、首次带参启动等也不作为当前结论。旧补丁不是正常授权。

## 本阶段方法沉淀

问题是把配置字段、容错返回、登录状态和业务成功混作一件事；直接写引用扫描又漏掉了整块写入。成熟处理方式是从加载/复制边界恢复结构，再沿字段的生产者和消费者分别验证。已将这一规则及 CDB 显式进制、离线输出边界写入项目技能。按用户本地范围约束，本阶段未查询在线资料；加解密 API 身份保持未决。

本轮完成了一个本地配置结构定位步骤；**没有取得正常授权，没有新的解码或授权后行为证据。**
