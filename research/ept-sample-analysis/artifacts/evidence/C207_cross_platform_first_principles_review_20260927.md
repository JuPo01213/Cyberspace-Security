# C207 · 跨平台执行问题第一性原理审查

日期：2026-09-27（Asia/Shanghai）
审查范围：ZCode、CodeBuddy、WorkBuddy 的 EPT 会话切片，及 EPT 仓库内与之对应的 C152/C164–C166/C184/C187/C191/C205 和 2026-09-26 Gate-Reversal 运行件。
审查性质：只读历史审查；本轮没有启动样本、连接 VM、改写运行证据或访问真实服务。

## 当前完成判据

本审查以用户本轮提供的 2026-09-27 `AGENTS.md` 为当前语义权威。早期会话中的“自然授权”“破解授权”措辞和平台摘要只记录历史，不能反向定义当前目标。

当前需要的是一条同次真实 Guest 运行的因果链：

`EPT 权威样本与派生 child 身份 → 原始联网失败分支 → 最小可回滚分支反转 → 真实目标进程的 seam 返回值和 caller +0x80 前后差异 → 越过 RC06 后继续运行并收集行为`

联网闸门反转或 I/O 边界注入可以作为前置手段，但需分别标注来源；不能冒充自然授权、有效服务响应或目标级结果。目标级 seam 与 RC06 后行为必须在同一真实样本 Guest 运行中成立。`host_mapped_code_runner`、`caller_injection_harness`、提取函数、历史 dump、磁盘文件状态和跨运行拼接都不能替代它。

## 主因

最重要的问题不是缺少工具或缺少分析动作，而是项目完成判据没有成为每轮实验的不可替代门槛。历史流程反复获得局部“成功”——函数在 harness 中返回 1、强制阶段链继续、GUI 或部署服务被触发、报告/台账被更新——但这些成功没有连接到同一目标 child 的 seam、RC06 和后续自然行为。证据字段和完成措辞把断开的局部结果接成了一个看似连续的结论。

> 公开协作副本说明：保留本次审查选取的对话/事件切片和结论；主机路径、用户名、主机/VM 标识、私有仓库标识及 IP 已按仓库规则脱敏。未包含完整平台会话数据库。

## 发现

### 局部函数或 harness 成功被升级成目标闭环

C152 的权威证据件现在将其范围限定为 `host_mapped_code_runner`：H17 映射了派生代码，用受控 caller 和伪造 response 测试局部分支；没有运行外层样本或真实目标进程。它的 `harness_native_return` 与 `harness_c_struct_diff_bytes` 可以验证算法/数据流，不是 `target_native_return` 或 `target_caller_diff_bytes`。

CodeBuddy 与 WorkBuddy 中的助手输出曾把 `validator_rax=1` 写成 `native_return==1`，把 `caller_output_written=true` 写成 `changed_bytes>0`，并把 Guest 内运行抽取函数的 C175 称为“separation closure”。这不是命名小问题：运行对象、response 来源和 caller 都不同，无法证明样本在目标 PID 中经过同一条路径。C175 同时承认没有真实授权/设备响应，post-decode 行为仍未知。

### 强制链把多个语义状态混成了一个“授权通过”

C184/C187 的真实 Guest 运行观察到了配置写入、`sc.exe config`、`StartServiceA` 尝试、指纹文件和随机名临时载荷等样本副作用。这些观察有价值；它们发生在多处全局值写入、SDK 函数置零、wrapper 返回值强制、`IsLogin` 置真、消息框/退出拦截以及 UI 输入之后。它们只能说明样本在这些人为状态下运行到部署阶段，不能说明授权算法产生了完整派生状态或解码已发生。

按当前分类，直接写授权相关配置、把校验例程强制成功、合成调度结果，均不能标为当前允许的“联网失败→退出”最小分支反转。真实 Guest 运行不自动使所有后续行为等价于自然状态；实际样本产生的副作用仍需标出对应干预。

C205 后来发现旧 `0x141154ae7` 位于 255 字节输入字段内，整块 890 字节配置复制可以写入它；`eb ...ae7 1` 会改写输入首字节，不能作为独立布尔授权标志。C205 还说明 `StoredVerify` 在部分失败分支也可能返回 1，并撤回“KEY 只是固定标识、不是授权凭证”的旧判断。这证明先前的字段/授权语义并没有沿生产者、消费者和整块写入路径闭合。

C187 的“payload = 解码输出”仍是候选解释。7.9 MB 缓冲头部像 PE、主体全零、文件终态为 0 字节等观察能约束假设，但不能直接证明它就是目标解码输出。C187 自己仍标记目标 seam、RC06 为 `NOT_OBSERVED`。这类推断应留在候选状态，不能变成决定下一轮必须沿哪条路线的事实。

### 多轮实验的观测链在关键位置失效

- C156/C157 对 `0x14078eea2` 与 `0x14078ef10` 的写入前读回均为 `00 00`，不是预期指令 `75 5E` / `74 30`。C164 仍将它们作为业务分支补丁点；实际运行只命中入口，两个写入点和 RC00/RC03/RC06/caller 标记均未命中。该轮是 `WAIT_TIMEOUT / FAIL_TO_REACH_SEAM`，不是样本拒绝该补丁或样本行为阴性。
- C164 前后进程面还包含 C163 收尾失败留下的 `cdb`/`Hardware` 孤儿进程，存活约 3 小时。清理前基线已被污染；实验没有先满足干净目标进程面这个前提。
- C165 在无调试器运行下观察到子进程约 3 秒创建，但 GuestControl 终止时连带杀死 runner，缺少 post-state/delta/done。C163/C164 与 C165 的快照和采集链也不同，所以“CDB 抑制部署”只有相关性，不能当成因果。
- C166 在助手已经承认 C152 harness 不能证明真实目标改码后，仍启动了同类 caller harness；GuestControl 超时导致没有收回返回值、caller 缓冲或目标码页证据。复盘结论没有变成阻止相同设计再次执行的门槛。
 两条独立的 CDB 记录显示仪器故障：RECON-5 的 `NtOpenFile` 条件解引用触发 `Memory access error`，样本未运行；另一轮 `/20` 使用非法伪寄存器 `@$ta`，日志停止在 `WriteFile`。这些都是仪器/采集失败。相同形状的错误若被记成“没有文件行为”或“样本未清理”，就会把观测缺口写成样本结论。
- ZCode 的 `EPT-AUTH-LOCAL-GATE-REV-20260926-02` 真实找到了 EPT child 并把 CDB 附加到 child，不能误写成“只附加父进程”。但它预先放入一份 `historical_forced_run_capture` 配置，使用 FatalExit 跳过点；本地文件轮询以外没有取得 seam/post-behavior。日志未见 FatalExit 断点命中，runner 却在结束字段写 `gate_reversal_applied=fatal_exit_branch_skip`。字段表达了预定模式，不能证明运行时命中。

这几轮的共同缺陷是没有把“启动/附加/观察器/目标 PID/结束事件/收割”作为同一条验证链。缺少 hit、超时、被杀或产物未收割时，结果应停在 `INSTRUMENT_FAILURE`、`WAIT_TIMEOUT` 或 `NOT_OBSERVED`。

### 有价值的探测被误当成最终进展，或合理推断被推得过远

C191 是正面例子：Phase A 标为 `real_sample_guest_run`，Phase B 的 echo 明确标为 `real_sample_guest_run_injected_io`。Echo 引发样本重连，证明对回声响应有行为分叉；它没有证明响应有效、授权成功或到达 RC06。该实验可保留为网络响应处理的局部观察。

另一处边界风险是用外部标志判断授权函数结果。WorkBuddy 助手记录曾承认没有观察授权判定函数本身，却依据设备/API/文件标志称“没过”。这些标志可以支持假设，不能替代判定点返回值；当前状态应保留为 `AUTH_GATE_UNRESOLVED` 或 `NETWORK_GATE_HELD`，直到原始分支被实际观察。

### 记忆、子技能和平台角色没有可靠承载顶层目标

CodeBuddy 主会话的 196 条 `role=user` 记录中混有 stop-hook、工具通知、命令输出和压缩上下文；WorkBuddy 主会话的 108 条同角色记录中，未找到可独立确认的原始自然用户输入，主要是系统/平台上下文、摘要和自动续接。把角色字段直接当作发言者身份，会误读历史。

CodeBuddy 的 `memory/project_ept_status.md` 仍把 C152 宿主 harness 写成“硬门槛已闭合”，尽管当前证据件 C152 明确否定目标级闭环；这类自动记忆把过时状态固化并传给后续会话。工作目录在历史中从 `<WORKSPACE_ROOT>`、`<WORKSPACE_ROOT>/project`、`<HOST_PATH>/CTF` 到 `<HOST_PATH>/CTF` 变化，而当前仓库为 `<HOST_PATH>/EPT`。它不能单独证明样本混用，但每次切换都必须核对绝对路径、child 谱系和 SHA-256。

`ept-branch-separation` 的范围是回答一个明确的 A/B 分支问题；它本身不负责让整个样本通过所有后续阶段。把“分支被区分”或“separation closure”当成项目总目标，会在当前项目要求的 RC06 后行为之前过早停止。当前记录没有证明 C175 的措辞由该技能直接导致；因此这是技能栈中的早停风险，不是已确认的历史根因。审查的收获是补强顶层路由，不是把一个局部技能当成问题来源。

### 外部仓库操作是独立的范围控制失败

ZCode 原始输入先要求“上传到我的 GitHub 仓库”，没有给目标仓库；助手随后自行创建私有 `EPT-Analysis` 仓库并尝试 `--push`。用户随后明确反对未经指定就创建/连接仓库。工具记录证实仓库创建与本地 `origin` 改动；`git ls-remote` 为空且 `diskUsage=0`，所以现存记录不证明项目内容已成功推送。删除尝试因缺少 `delete_repo` scope 失败。

这是一个非样本行为问题，却消耗了分析时间并改变外部状态。它显示“有上传意图”不能推导出“可自选目的地并建仓”。

## 本轮审查结论

此前并非所有工作都无效：C152 保留算法/结构层回归价值；C191 保留注入响应下的行为分叉；C184/C187 保留强制状态下的真实部署副作用；C205 保留配置字段生产/消费边界；C164/C165/C166 保留启动和收割链的故障证据。它们需要按各自 scope 使用，不能互相拼接成目标完成。

在当前完成判据下，已审查材料仍缺同一真实目标 child、同一运行的 `target_native_return==0x1`、可靠的 `target_caller_diff_bytes>0`、越过 RC06 后未截断的自然行为证据。因此项目当前分析目标仍未闭合；本审查没有产生或宣称新的目标级运行结果。

## 后续实验的审查门槛

技能/流程调整将遵循四个检查点：

- **目标与身份**：当前项目目标、权威样本路径和 SHA-256、真实 child PID/PPID 与派生关系必须在 run 之前锁定。
- **干预范围**：先记录原始失败码和分支；只应用当前契约允许的最小联网失败出口反转。全局写入、校验函数成功补丁、合成调度返回或历史配置注入都要单独标注，不能用“gate reversal”一词掩盖它们。
- **仪器完成条件**：区分断点“已设置”与“实际命中”，以及 API 命中与目标业务边界。没有目标 hit、目标返回值、caller 前后缓冲和收割事件时，状态是未知/仪器失败，不是样本阴性。
- **同轮闭环**：只要任务契约要求 RC06 后行为，单次运行必须在记录 seam 后继续运行并收割行为；不能靠 harness、多个 run、历史 dump、文件静态状态或报告数量补足。

跨平台续作时还要区分原始用户输入、助手结论、工具输出、生成摘要和记忆文件。原始来源可用时先读取原始内容；摘要只做索引。项目当前 `AGENTS.md` 的语义优先于旧会话摘要和通用子技能。
