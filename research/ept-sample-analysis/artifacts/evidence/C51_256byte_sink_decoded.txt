   What the controls ruled OUT, first, because both were my own candidate judges:
     * instruction COUNT per page is worthless: the two known DATA pages decode MORE
       densely (1336 / 1264 ins) than the two known CODE pages (1012 / 1011), because short
       garbage bytes decode into 1-2 instruction bytes. "It decodes" is not "it is code"
       (same lesson as the 22 % reachability error, now with numbers).
     * the shift test is a null result: +0/+1/+2 give identical counts in every row
       (71/71/71, 3/3/3, 1/1/1, 0/0/0, 83/83/83). The walk is deterministic, so alignment
       sensitivity as I built it measures nothing - do not cite this column.
     * coverage and entropy separate the reference classes weakly/partially: code covers
       99.1-100.0 % at entropy 5.98-6.64, data 95.4-96.2 % at 7.85-7.88, and the target sits
       BETWEEN them (98.1 % / 7.42). So neither can decide the target - and that is exactly
       why the first version of this script, which trusted an invented entropy cut of 7.4,
       got the wrong answer with a straight face.
   What does decide it, in the same table: the fraction of FAR (rel32-shaped) call/jmp
   targets that land inside the image. Code 100 % and 99 % over 109/154 samples; data 71 %
   and 70 % over 35/46; the target 95 % over 65. Data reaches ~70 % only through its
   short-range jumps; a 95 % hit rate on far displacements is a displacement-distribution
   property of real code, and the target has it.
   Plus one non-statistical argument: 0x14117c32e is a call target computed from verified
   plaintext .text (C50), so it is an instruction start by construction; decoding from it
   gives 83 instructions in 0x140 bytes, a `ret 8`, and then eleven int3 padding bytes.
   推断 (not observation): the held .Sq> head is decrypted runtime code, VMProtect-MUTATED
   (pushfq/popfq pairs, not/setae on a scratch byte, movabs garbage into an unused register
   - mutation junk, which is also why its page entropy is 7.4 rather than 6.x).
   Consequence for the goal: the 256-byte sink is NOT an unknown-address callee. It lives in
   bytes already on disk here, so the append action needs no new run to be characterised
   down to this block. What still needs a capture is the next hop: all 11 call targets out
