## 4.0 先立仪器口径，否则后面每条数字都没有意义

1. **主仪器是 capstone 全窗口滑移 + `.pdata` 条目归属**，Ghidra 只作第二意见与反编译视图。裁决依据在 §4.9：9 处分歧里 capstone 57 条全为真，Ghidra 50 条含 1 条假阳性，且 Ghidra 有 8 次"该地址根本没解码"。
2. **REX 重影规则**：滑移会在 `lea rdx,[rip+…]` 的**后一字节**再造出一条同目标、错地址的 `lea edx`；`74 40` 的 `0x40` 也会当 REX 前缀吃掉一条真 `call`（§4.4(5)）。⇒ **同目标、地址差 1 的两行 = 一条指令**；引用计数要折半，函数归属不受影响。
3. **BAD-SEED 规则**：跳转操作数落在"已解码指令的内部字节"时，该目的**绝不作为行走种子**，并把两侧解码都打出来让字节决定。C22 里 5 条 BAD-SEED 本夜逐条复点 ✓。
4. **`.pdata` 条目 ≠ 逻辑函数**（§4.3）。凡"某地址属于哪个函数""可达集多大"都要按条目口径说清。
5. **"能解码成指令"不是代码证据**：`main` 区间 46 个 512 B 窗口里，高熵区也能平均解出 2.6–3.2 字节的"指令"（§4.10）。判读只依赖熵与平均指令长两个量。
6. **本讲有一个新的总限定**：P3§3.8 测得同一 VA 区间在 C2 与 C6 两次运行里 **`.text` 哈希不同**（`0D291B31…` vs `5ae354e2…`）。⇒ **本讲每条地址级结论的适用范围是"C6 这一次运行流出的那份 `.text` 字节"**，不得写成"该样本的 `.text` 必然如此"。

## 4.2 函数表与捕获件身份（不运行样本就有 2,593 条边界）

**观察（本夜重解析）**：从磁盘 genB 的 `DataDirectory[3] = RVA 0x3f5d150 size 0x79e0`（落在**有磁盘字节的 `.)Bu`**，而段表里名叫 `.pdata` 的 `0x14116d000` `RawSize=0`）解析出 **2,593 条**合法 `RUNTIME_FUNCTION`：

* 归属：`.text` **1,694** / `.Sq>` **870** / `.)Bu` **29**；条目区间**两两不重叠、严格递增**（本夜重测：重叠对 = 0）。
* 尺寸：min 1 B / max 640,498 B / mean 1,775.6 B / 合计 4,496 KB；跨度 `0x140001000..0x143f55411`。
* **闸门函数被登记成 3 条**：`0x1407a3080..0x1407a3323`(675 B) + `..0x1407a341d`(250 B) + `..0x1407a3508`(235 B)，三者共享同一栈帧与同一 security cookie ⇒ **一个逻辑函数、三条目**（本夜逐条复点 ✓）。
* ⇒ 连带作废一条旧假设："函数边界以 `.pdata` 为准"。真实关系是 **`.pdata` 比逻辑函数更细**，所以 §14.33 当年把 10 处"两器函数名不同"解释成"Ghidra 合并了相邻函数"**方向反了**。
* 可达集 `246/1,694` 是**条目口径**，不能读成"246 个函数可达"。
* `.pdata` 内还有**真空洞**：5 个真实引用点（`0x14078fafa/fb42/fb6a/fb72/fbaa`）落在任何条目之外 ⇒ "函数表 = 全部代码"不成立。

**观察（捕获物三重校验，本夜重跑）**：运行时头与文件头逐项相同（`MZ`、`e_lfanew=0x80`、`machine=0x8664`、`nsec=10`、`SizeOfImage=0x3f83000`、`EP=0x235f67b`、`ImageBase=0x140000000`）⇒ 镜像基址未被 ASLR 改动；`.text` 熵 6.614；随机抽 12 个函数按 `.pdata` 边界线性反汇编，11 个解码字节数与声明长度逐字节相等。
**限定**：另有 `_RDATA`/`.fptable`/`.Sq>`/`.bs]`/`.rsrc` 等 10 段，其中只有 `.bs]`(4 KB)、`.)Bu`(32,545,792 B)、`.rsrc`(120 KB) 带磁盘字节。

## 4.3 交付① 授权判定的输入表

**`FUN_1407a3080`（闸门）** 对四个 `.data` 全局做短路合取：

```
0x1407a30b2  cmp dword [0x141154ced], 1 ; jne 0x1407a30da
0x1407a30bb  cmp dword [0x141154cf1], 1 ; jne 0x1407a30da
0x1407a30c4  cmp byte  [0x141154ae7], 0 ; je  0x1407a30da
0x1407a30cd  cmp dword [0x141154ce9], 0 ; je  0x1407a30da
0x1407a30d6  mov bl,1  /  0x1407a30da  xor bl,bl
```
四个全局的 `.text` 内 RIP 引用数 **4 / 5 / 6 / 5**（`C19`/`C27` 本夜复点一致：28 行、3 个 owner 函数）。

**合取实例的真实数量是"3 个站点 / 2 个函数"**（不是早期写的"≥4 处内联"）：

| 函数 | 站点 | 形式 |
|---|---|---|
| `FUN_1407a3080` | `0x1407a30b2/bb/c4/cd` | 四全局合取（闸门本体） |
| `FUN_1407a3510`（5,165 B） | `0x1407a354f/558/561/56c` **和** `0x1407a4700/70d/71a/727` | **同一函数内两处**独立合取，且顺序不同（`ced,cf1,ae7,ce9` vs `ced,cf1,ce9,ae7`） |
| `main`(`FUN_1407a4b90`) | `0x1407a6a05/a0d/a16`、`0x1407a7aec/af5/afd/b06` | **不是完整合取**：全局 vs 寄存器比对（见 §4.4） |

**观察（本轮扫出的第五个全局）**：`0x141154d10` 被 `FUN_1407a3510` **写 3 次**（`0x1407a35b7` 写 `eax`、`0x1407a3629` 写 `1`、`0x1407a3633` 写 `ebx`）并在 `xor ebx,ebx` 后立刻被读、按符号分岔 ⇒ 形状是"算一次、缓存进 `0x141154d10`、以后看缓存"。它**不在阶段目标给的四锚点里**，此前所有清单都漏了。
**未决**：四个 `.data` 全局的**写入者**——`.text` 内没有任何 RIP 相对写入，只有 `0x1407a320e` 处 `lea rcx,[rip+g3]` 把地址交给了 SDK 调用 ⇒ 写入经指针发生在 SDK/未捕获侧。"无 RIP 写入"≠"无人写入"。

## 4.4 交付② 两条分支在字节上分离

### (1) 闸门内三个出口
```
0x1407a3111 test bl,bl ; 0x1407a3113 jne 0x1407a311c
   FALSE -> 0x1407a3115 xor al,al ; jmp 0x1407a341d          (a) 返回 0
   TRUE  -> 0x1407a311c FUN_1403b34d0(0x140f92550,0x7530,0)   (token 地址作为实参，本讲不解码)
```
阶段链每环都是 `call <SDK>; 记日志(码); test ebx,ebx; je <成功继续>`，**失败反而 `mov al,1`** ⇒ (b) `init/option/cardlogin/islogin` 四处 `*_failed_soft_allow` 与 (c) 阻断叶。

### (2) "两处 switch"其实是一条两级跳转表（本夜从字节完整重解）
```
A 级 0x1407a3260: eax = rbx + 0x3d ; cmp eax,0x28 ; ja 0x1407a3285
                  movzx eax, byte [rdx+rax+0x7a3448]          ; 41 项字节索引表
                  mov   ecx,  [rdx+rax*4+0x7a3440]            ; 2 项目标表 = [0x1407a32b6, 0x1407a3285]
                  add rcx,rdx ; jmp rcx
B 级 0x1407a3285: eax = rbx + 0x27 ; cmp eax,0x27 ; ja 0x1407a32b6
                  41→40 项字节表 @0x7a347c，目标表 @0x7a3474 = [0x1407a32a3, 0x1407a32b6]
```
两张表的 dword 表尾**正好接上**自己的字节表（`0x7a3440+8 = 0x7a3448`、`0x7a3474+8 = 0x7a347c`）⇒ 布局由算术自证，不是我猜的。逐码解出：

| 叶子 | 含义 | 命中码 |
|---|---|---|
| `0x1407a32a3`（`lea rcx→0x140f92770 "cardlogin_failed_soft_allow"`; `mov al,1`） | **放行** | 恰好 **8 个**：`-39,-38,-16,-4,-3,-2,-1,0` ✓ 与旧文逐码相同 |
| `0x1407a32b6`（`lea rcx→0x140f92740 "cardlogin_denied_clear_or_block"`; `call FUN_1407a3000`） | **阻断/清理** | A 级 7 个 `-61,-41,-28,-27,-23,-22,-21` + B 级 32 个 + 两级 `ja` 越界值 |
| `0x1407a3285` | 落回 B 级 | A 级其余 34 个码（`-60..-24` 中除去那 7 个） |

⇒ **更正一处计数**：B 级表是 **40 项**（码域 `-39..0` 含端点），旧文写"41+39"。放行集不变。
⇒ **与 §4.6 的关系**："0 个 `switch`"只对 `main` 成立；闸门函数里有真 `jmp rcx`×2。两个函数结构不同，不能互相外推。

### (3) 调用点侧才是真正的进程分岔
```
0x1407a6a4e call FUN_1407a3080 ; … 0x1407a6a6a test bl,bl ; je 0x1407a7b18
0x1407a7aec cmp [0x141154ced], r11d ; jne 0x1407a7b4f
0x1407a7af5 cmp [0x141154cf1], ebx  ; jne 0x1407a7b4f
0x1407a7afd cmp [0x141154ae7], r12b ; je  0x1407a7b4f
0x1407a7b06 cmp [0x141154ce9], r12d ; je  0x1407a7b4f
0x1407a7b0f call FUN_1407a3080 ; test al,al ; jne 0x1407a7b4f
0x1407a7b18 xor ecx,ecx ; push rdx ; call 0x1417612fa ; int3      ← 终止块
```
⇒ **`main` 侧终止块进入条件 = 五者同时成立**（`ced==r11d ∧ cf1==ebx ∧ ae7!=r12b ∧ ce9!=r12d ∧ gate()==0）。**"闸门返回 0"并不单独导致终止**——这句把 §14.38(4) 的"返回 0 ⇒ 终止"改窄了。
⇒ `0x1407a7aec..b20` 这 26 字节 **Ghidra 一条都没有**（全答 `0x1407a7b21`）⇒ 判为 **capstone-only**：可引用其分岔形状，不可当独立证据。

### (4) 同一判据在载体里极性相反（这是我 own 的一条口径被推翻）
```
载体 #1 不成立汇合点 0x1407a357a: xor ebx,ebx → … → mov eax,ebx → ret  ⇒ 返回 0
载体 #2 不成立汇合点 0x1407a48a4: 定长日志(标题「固定部署」@0x140f92898,
                                   正文「未找到有效配置，请先使用 -k 完成授权配置！」@0x140f928a8)
                                   → mov eax,1 → 同一 epilogue ⇒ 返回 1
```
⇒ **"返回 0 的唯一来源是合取不成立"只在 `FUN_1407a3080` 内成立**；极性是每个实例自己的属性。以后任何"某全局为 0 就是未授权"都必须先指明是哪个实例。
⇒ 载体**从不调用** `FUN_1407a3000` ⇒ 阻断执行者不在载体里。

### (5) `main` 的返回值管道 + 一处假调用点
`0x1407a7b4f call 0x1407a3510 ; 0x1407a7b54 mov ebx,eax ; … ; 0x1407a534a mov eax,ebx ; ret(0x1407a5375)` ⇒ **`main` 的返回值就是载体的返回值**；中间那条 `test eax,eax / jne` 只决定要不要多跑一次 `call 0x14079a100` ⇒ **它是"额外动作开关"，不是 soft/hard 分岔**。
`C19_gate_readers.json` 的调用点清单里 `0x1407a7b0e` 是 **REX 重影**（`0x1407a7b0d` 的 `je` 操作数就是 `0x40`，滑移把它当 REX 前缀吃进真 `call`）⇒ **真调用点是 `0x1407a7b0f`**；这种伪指令目标完全正确，"目标一致性"自检抓不到。
**观察（返回值传递链已验证）**：epilogue 里 `call 0x1407b06b0`（cookie 检查，30 B）两条分支都只动 `rcx`，**全程不写 `rax`** ⇒ 叶子写的 `al` 就是调用点 `test al,al` 用的那个 `al`。

### (6) 出口"干什么"落到地址上
| 出口 | 动作集合（判据） |
|---|---|
| (a) 闸门返回 0 | 无文案；`main` 侧是五条件合取的终止入口 |
| (b) 阶段失败放行 | **只有一条英文标签**（`lea rcx,<tag>; call FUN_14078fc90`），无弹框、无清理，返回 1 |
| (c) 阻断 | `mov ecx,ebx(码); call FUN_1407a3000` → 该函数调用 **`FUN_1407a2a90`**（体内四条 `rmdir /s /q "{C,D}:\Windows\System32\{Logs,HardwareLogs}"`，引用点 `0x1407a2def/e64/ed9/f4e`），并以四参形状 `(rcx=0, rdx=0x140f924c0「授权状态异常，本地配置与固定部署已清理。」, r8=0x140f924f8「授权验证」, r9=0x10)` 弹框，随后 `call 0x141a1ff1b` |
| (d) 载体 #2 不成立 | **同样四参弹框形状**，但**不**调用 `FUN_1407a3000`/`FUN_1407a2a90`，返回 1 |
| (e) 载体 #1 不成立 | 无文案，返回 0 |

⇒ **"hard" 由动作集合定义，不由形容词或文案定义**：只有 (c) 同时具备"带错误码 + 弹框 + 删日志目录"。
⇒ **网络阶段只在成功支被装填**：`test ebx,ebx@0x1407a3172 / je@0x1407a3174` —— Init 返回 0 才 `mov edx,0x405(=1029); lea rcx,[0x140f92688 "yz.hwid001.com"]; call 0x1403b3280` ⇒ **fail-open 时连服务器地址都没被装填**（观察）。
⇒ **`FUN_1407a4a90`**（两条 `sc.exe config "AntiCheatExpert …" start= delayed-auto`，32 B）在 `.text` 直接 `call` 边里前驱为 0 ⇒ 只否定"有直接调用边"，**不判死代码**。

### (7) 剩下那个未决量不能用当前静态面关闭

`C59` 已把地址前提纠正回来：`0x141a1ff1b` 与 `0x1417612fa` **不是幻影**，正确的明文调用点分别是 `0x1407a305c` 与 `0x1407a7b1b`。但两目标的函数体 RVA 都超出当前 `stream_text.bin` 的 8,257,536 B 捕获窗口；因此当前静态面能证明“谁被调用”，不能证明“被调用后是否终止进程”。

这不是 `C55` 的旧式“明文中不存在”阴性，而是 **`VALID_UNOBSERVABLE_ON_THIS_BASE`**：调用点可见，被调方本体不可见。阻断支是否也终止进程仍需行为观测或 `.Sq>` 去虚拟化；这个未决量不应再由旧的页字节反汇编结果解释。

### (8) 地址口径复核：`C57`–`C59` 撤回 `C55`/`C56` 的旧翻案

`C57` 先从输入内嵌 PE 头独立证明：`stream_text.bin` 的 offset 0 是 `MZ/PE` 头，`ImageBase=0x140000000`，所以本捕获的唯一地址公式是 `VA=ImageBase+stream_offset`。`BASE=0x140001000` 只是把所有结果整体抬高一页，并非这个流的起点。

`C58` 用两条独立路径（固定字节签名与 Capstone RIP 操作数）复核了原文地址：

| 正文写的 | 字节上真的 | 差别 |
|---|---|---|
| 全局 `0x141154ced/cf1/ae7/ce9` | 同一组地址 | `83 3d disp32 01` 的精确命中与 RIP 反查均回到该组；`0x141155…` 是旧映射产生的假地址 |
| 闸门合取 `0x1407a30b2/bb/c4/cd` | 同一组地址 | 真实字节逐条解出四个短路比较并汇聚到 `mov bl,1`/`xor bl,bl` |
| 载体两处合取 `0x1407a354f/558/561/56c`、`0x1407a4700/70d/71a/720` | 同一组地址 | 两处均可由字节独立重算；第二处不在 `main` |
| `main` 的混合比较 `0x1407a6a05/a0d/a16`、`0x1407a7aec/af5/afd/b06` | 同一组地址 | 这些是全局与寄存器的比较，不改称完整四全局合取 |
| 完整合取实例 | **3 个 / 2 个逻辑 owner**；宽口径 RIP 引用扫描为 6 簇 / 20 站点 | C58 明确区分完整合取与 `lea/mov`、main 混合比较 |

结构层面（四状态量、短路顺序、载体两处实例、main 五条件形状）经 C58 复核后仍成立；被推翻的是 `C55/C56` 两个旧仪器的“地址不存在/整体低一页”解释。C55/C56 保留为历史失效件，不再作为当前结论来源。C59 另行证明两个争议 `.Sq>` 目标的调用点真实存在，但被调方本体超出当前捕获范围。

## 4.5 交付⑤ `-k/-n/-m`：解析与首个数值消费点都有代码级证据

**解析（观察，全部在 `main` 内，helper = `FUN_1407be830`，24 个比较点）**：`--nsp-runtime-child`(5) `--shift-open`(4) `-reboot`(3) `-ins`(2) `-c` `ept` `del` `-h` `-now` `-k` `-n` `-m`。

| 选项 | 落地语义（逐条读自 `0x1407a54a0..0x1407a5640`） |
|---|---|
| `-k` | 取下一个 argv，拒绝空串与单独 `-`；`CALL 0x1407d86e0(dst,src,0xfe)` ⇒ 拷进 `[RBP+0x1f90]` 的 **254 字节栈缓冲**；标志 `[RSP+0x65]=1` |

| `-now/-h/-reboot` | 纯布尔标志 |

**消费（观察，切片件 `C11_main_slot_slice.json`：6,328 条指令 / 22,961 B = 98.0% 函数字节可解码）**：
```
入口  1407a4bcc  mov [rsp+0x70], r13d      ← 同一个 dword 的第一辈值是 argc
1407a5326  call FUN_1407a1fa0(argc, argv, &out)   ← argc 的真实消费者

1407a5865  cmp ecx, 1    / jne 0x1407a6ad1 ← ==1 特判
```

⇒ **`[RSP+0x70]` 至少承载两辈不同变量**（先 argc、后 `-n`），"谁读这个槽"必须按活跃区间回答；`[RBP-0x80]` 同样被复用。
⇒ 推断（从判定形状、不是从名字）：`-n` 是**下标类**参数，`-m` 是**带符号模式**参数。
⇒ **作废**：旧 §14.31(2) 的"消费点被**控制流平坦化**挡住"。字节层面在代码区内未发现任何间接转移、也没发现"状态地址入栈"模式（40 处 `lea`+`mov 槽` 更像编译器把字符串/表指针物化到栈上）⇒ **我把反编译器产物当成了二进制事实**。

## 4.8 本轮新发现：投放文件名的**格式串与格式化调用点**都在明文里

`C37b` 在复核 §14.32(4) 时否掉了那条负结论：

```
0x140f92344/0x140f92348  UTF-16 字面量 "%sEPT_%08X_%08X.exe"      ← 旧文记为"两种编码均 0 命中"
邻域：0x140f92334 处是 ASCII 选项表 "ept\0del\0-ins\0"，0x140f92370 处是 UTF-16 "--nsp-runtime-child"
同一扫描还找到 4 条 ASCII 字面量 "del /f /q "C:\Windows\Temp\HardwareTask.xml" >nul 2>nul"（C:/D: 各一条）
```
一次覆盖全窗口（8,253,425 个解码单元，7.06% 不可解码）的 RIP 扫描给出引用点（`C37c`/`C37d`）：

```
0x1407a2090  call 0x1407a1f00 ; mov edi,eax
0x1407a2097  call 0x1407a1f00
0x1407a209c  mov [rsp+0x28], eax
0x1407a20a0  mov [rsp+0x20], edi
0x1407a20a4  lea r9, [rbp+0x330]
0x1407a20ab  lea r8, [rip+0x7f0296]        -> 0x140f92348 "%sEPT_%08X_%08X.exe"
0x1407a20b2  mov edx, 0x104                 ; 260 = 缓冲区大小
0x1407a20b7  lea rcx, [rbp+0x20]            ; 目的缓冲
0x1407a20bb  call 0x140789eb0               ; (dst,count,fmt,arg4,arg5,arg6) —— snprintf 形
```
两个 `%08X` 的实参正是**对 `0x1407a1f00` 的两次调用**的返回值 ⇒ `EPT_<8hex>_<8hex>.exe` 的两个 32 位分量来自同一个 helper 的两次取值，这与磁盘上观察到的命名模式（P3§3.5）第一次在代码层对上。
**归属（观察）**：`0x1407a20ab`、`0x1407a2435`、`0x1407a2451` 三点全部落在 `.pdata` 条目 **`0x1407a1fa0..0x1407a258d`（1,517 B）** 内——也就是 §4.5 里 `main` 用 `(argc, argv, &out)` 直接调用的那个函数；同一函数里还有 `--nsp-runtime-child` 的两处引用（`0x1407a2435` 经 `0x1407b48f0` 且 `r8d=0x26`，`0x1407a2451` 经 `0x1407af5d0` 且 `edx=0x13`=19=`strlen("--nsp-runtime-child")+1`）。

⇒ **三条净结论**：
1. **作废**：§14.32(4)"命名格式串在两种编码下均 0 命中 / 其拼装代码不在已恢复明文内"。格式串、缓冲区、大小、格式化调用点全在明文里，且在一个**从 `main` 直达可达**的函数内。
2. **收紧**：旧文"投放点 = `FUN_1407c1f44`"仍然对，但它引用的是 `.data` 里**已经构建好的**完整路径串（`0x14115b120`）；**构造**该名字的站点在 `0x1407a1fa0` 这一族。两者不是同一个函数，此前把后者当成唯一投放实现。
3. **顺带更正引用计数口径**：`--nsp-runtime-child` 在 `C6_anchor_xrefs.tsv` 里记 4 处，本夜按 REX 重影折半后是 **2 条真指令**（`0x1407a2435`、`0x1407a2451`，均在 `0x1407a1fa0` 内）⇒ 旧文把它归给 `FUN_1407a4b90`(`main`) 是**归属错位**。
**未决**：`0x1407a1f00` 返回的是什么熵（tick / PID / RNG）——一次 30 字节的反汇编就能判，是本轮之后最便宜的下一条检查。`0x140789eb0` 是否真为 `_snwprintf` 家族也仍是形状判读（被调方在明文里，可继续读）。

## 4.14 追加：命名熵源与格式化例程的真身（`C38`，纯离线）

`verify_branch_offline.py` 把 P4§4.16 里前两条未决直接读穿了。

**`0x1407a1f00` = 带持久状态字的 MurmurHash 型混合函数**（160 B / 51 条指令）：

```
0x1407a1f27  mov  edx, [rip+…]        -> 0x14116c540   ; 读状态字（该地址在已捕获的 RG2 窗口内）
0x1407a1f2d  mov  r9d, 0xd00dfeed                      ; 状态字为 0 时的种子
0x1407a1f1c…0x1407a1f22  四次 call 0x1413ec58f / 0x1416a5c8c / 0x1415099cb / 0x1419d0758  ; 全在 .Sq>（未捕获）
0x1407a1f1f/0x1407a1f3b..48  xor ebx,eax ; xor r8d,ebx ; xor r8d,[rsp+0x34] ; xor r8d,[rsp+0x30] ; xor r8d,eax
0x1407a1f5f  add eax, 0x9e3779b9                       ; 黄金比例常数
0x1407a1f78  imul edx, ecx, 0x7feb352d                 ; fmix 常数
0x1407a1f85  imul edx, ecx, 0x846ca68b
0x1407a1f6d  mov  [rip+…], edx  -> 0x14116c540         ; 回写状态字
0x1407a1f92  cmovne r9d, edx ; mov eax, r9d
```
⇒ **观察**：投放名里两个 `%08X` 的分量来自**同一个函数被调用两次**（`0x1407a2090`、`0x1407a2097`），而该函数每次调用都改写自己的状态字 ⇒ ** consecutive 调用必然给出不同值**。
⇒ **观察（机制取代猜测）**：P3§3.5 说"追加块由运行时产生、跨运行不可复现"，当时只有三条实测值支撑；现在给出**为什么**：`rdtsc` 不在其中（`rdtsc present: False`），熵来自 4 个壳侧调用 + 一个可捕获的状态字。⇒ 关掉最后一条"也许能离线预测下一跳文件名"的侥幸；同时给出一个**新的离线可查项**：状态字 `0x14116c540` 就在已捕获窗口里，可读它的当轮快照值。
⇒ **推断**：这是 MurmurHash/xxHash 风格的 avalanche 混合，不是密码学 PRNG；没有 nonce/种子来自服务器的证据。

**`0x140789eb0` = `_snwprintf` 家族的薄包装**：`call 0x140786c20` 取回一个块指针 → `mov rcx,[rax]` → `call 0x1407be620(rcx, dst, count, fmt, …)` → `test eax,eax / cmovs eax,-1`。⇒ 失败返回 -1 的形状与 CRT 宽字符格式化一致；真正的转换循环在 `0x1407be620`（下一步读它即可完全坐实）。**观察 = 形状；推断 = 具体 CRT 例程名**（被调方在明文内，可继续离线读）。

**`r11d/ebx/r12b/r12d` 的来历**：`0x1407a7900..0x1407a7aec`（484 B，解出 119 条指令）内**没有任何一条对这四个寄存器的写入** ⇒ 值来自更早处或调用帧。该阴性只覆盖这个窗口，不覆盖 `main` 的高熵区（P4§4.10）。维持未决，但排除掉"就地赋值"这一种解释。

**命名/重启函数 `0x1407a1fa0` 的子树**：369 条指令、41 个直接调用点、31 个不同被调方；`0x1407a1f00` 在其中被调用 **3 次**（不止命名块那两次），`0x1407af5d0`（追加串）2 次；~~未发现任何 `0x100` 立即数 ⇒ +256 追加块的写入者不在这个子树里~~ **这句本夜作废，而且是我读错自己的证据件**：`C38` 内有两个"256 立即数"清单，我引了 §2（格式化例程 `0x140789eb0`）那份的 `[]`，而同一件 §4（本子树）那份印的正是 `0x1407a21c0 / 0x1407a21d7 / 0x1407a21ff` —— **写入者就在这个子树里**，全文见 §4.17。

#### 追加（`C40`/`C40b`，纯离线）：我那句"转换循环在 `0x1407be620`"是**错的**

控制组 4/4 先过（同一台仪器在 `0x1407a30b2/bb/0d6/0x1407a3111` 解出与两仪器一致的 `cmp/cmp/mov/test`），然后：

- `0x1407be620` = **273 B / 77 条**，形态是 `mov`×32 + `movups`/`movdqu`（成批搬字节），只有 3 个被叫方，**格式化判据立即数一个都没有**（`0x25`/`0x30`/`0x39`/`0x2d`/`0x23`/`0x2b` 全零命中），`sub/cmp` 也没有 4..16 这种"数字位数"界。⇒ 它是**参数/缓冲搬运层**，不是转换循环。
- 沿 E8 调用边向下闭包（深度 ≤3、每层 ≤24 个新体，声明为**上界**不是普查）在 **`0x1407bbbf0`**（669 B / 189 条）里一次拿到 **`0x20 ' '`、`0x23 '#'`、`0x2b '+'`、`0x2d '-'`、`0x30 '0'`** —— printf 家族的**五个 flag 字符**齐了；它还有 `[r14 + rax*2 + 1]`、`movzx eax, [r14 + rcx*2]` 这种 **×2 步长**的表索引（宽字符表遍历的形状）。
- **【本条已被 `C43` 作废】**那句"只有 1 处"来自一次**只覆盖 43 %** 的线性解码（capstone 撞到解不出的字节就停），真实计数是 **8 处**，见下方 `C43` 表。保留原文只为留下"我是怎么错的"。
- 但 `'%'`（`0x25`）在整个已恢复 `.text`（RVA `0x1000..0x7da900`，约 8.23 MB 线性解码）里**只有 1 处** `cmp eax, 0x25`，在 `0x1401bfaf1`；上下文是 `xor/and/or` + 魔数 `0x55a98cc7` + `cmovl` 的位混合（**不透明谓词/平坦化风格**），与格式化无关。

⇒ **观察**：判定"是不是格式化引擎"的证据从"`0x1407be620` 本体"移到"它的 depth-2 被叫方 `0x1407bbbf0`"；五个 flag 字符 + ×2 步长表索引是同一条子树里拿到的。
⇒ **方法论自我更正（这条比结论重要）**：我原本写的判据"**格式化引擎必然比较 `0x25`**"是**无效判据**——它只对"用立即数比较做字符分类"的源码成立，**表驱动分类会让它恒为阴性**。所以"`0x25` 只命中 1 次"**不能**读成"这里没有格式化引擎"；同一条阴性也**不能**反过来读成"有"。⇒ 该判据已从 §4.16 的清单里划掉，替换为"看分类表基址与表内容"（表基址在 `r14` 里，本层明文看不到来源，需要下一层或运行期）。

**不能下的结论（明确禁止的写法）**：不得把 BR3/BR4/BR5 的停摆读成"走了终止支"或"走了继续支"。终止支的特征是 `int3` ⇒ 进程以 `0x80000003` 结束，而**进程根本没机会结束**（`T4 False` 表示它当时还活着）；继续支的特征是返回 `0/1`，同样没读到。停摆本身在 §3.13 的底座下**不是样本行为的证据**——同一台 VM 在样本从未启动的会话里也会丢 60–348 s 虚拟时间。

**为此安排的阴性对照（CTRL1，`arm9.sh`）**：同一套闸门、同一个 0.5 s tick 心跳，**样本不投放也不启动**，只跑一个 6 分钟的纯 CPU 循环。若纯 CPU 也出现同样的停摆 ⇒ "停摆"归底座，任何退出码臂在此环境下都不成立，本未决量应改记为**环境上限**；若纯 CPU 流畅 ⇒ 停摆是样本独有，值得继续加预算或换底座。

**这条未决量现在怎么收口**：静态侧已尽（§4.4(7)、§4.14 把两个 callee 定位到 `.Sq>`；`C41` 又把载体"全真"支与被叫方边界钉清）；动态侧要往前走只有一条实质路径——**把 VT-x 还给 VBox**（关宿主 HVCI/VBS，需重启）或换到不吃嵌套虚拟化的底座。这属"宿主级不可逆变更先报告确认"，**未执行**。在此之前，§4.4 的交付口径保持为：**两条分支在字节层已分离，唯一未决量"阻断是否也终止进程"在本 lab 当前底座下不可观测**。



### 4.15a BR6：把问题从"等退出码"换成"读 1 KB 内存"，两件事当场有答案

`C44` 给出一个此前被忽略的事实：`.Sq>` 从 `0x141174000` 起，而**手上那个 RG2 blob 覆盖到 `0x141200000`** ⇒ `.Sq>` 的头 557 KB 其实已经在盘上；两个 callee 分别在 `.Sq>` 内 +6.2 MB / +8.9 MB 处。于是未决量不再需要"采 15 MB"，而是**两次 512 B 的 `ReadProcessMemory`**。BR6 就按这个改法跑（判据在启动前写进 `judge_branch.py`）。

自检：`PEEK_CONTROL self=True bogus_pid=False`（正/负控制都如预期），且读回的 PE 结构与盘上头部逐项对得上（导入描述符 **13 条 + NULL 终止**、`FirstThunk` 以 16 B 步距铺开）⇒ **被窥探的确实是那个已加载镜像**，不是错进程。

| 读数 | 结果 | 口径 |
|---|---|---|

⇒ **这一臂把 §4.16-7 的"888 B 窄窗口臂"从'待跑'变成'已跑并交付'**：五个窗口全部读回（`WINDOWS_READ=5/5`），而退出码那条路依旧没走到（`BRANCH_DONE` 缺，判定 rc=2、不作任何分支主张）。

**但"全零"这件事本身还有一条更值得记的推论——我用已在手的旧件把它证伪了一半。** `RG2_region_0x140e00000.bin` 覆盖 `0x140e00000..0x141200000`，而 `.Sq>` 从 `0x141174000` 起 ⇒ 那份 RG2 运行**已经采到 `.Sq>` 的头 560 KB**。逐 4 KB 页量：

### 4.15b BR6 的流为什么断在 26 行：一个我自己造成的、但必须先分清的歧义

把六臂的"最后一行时间戳 − LAUNCH 时间戳"排成一列，得到的不是偶发故障而是一条规律：

| 臂 | LAUNCH（客户机钟） | 流里最后一行的落盘时刻（宿主钟） | 最后一行 |
|---|---|---|---|
| BR3 | 02:10:09.234 | 02:10:56（+47 s） | `TICK wait el=5 exited=False` |
| BR4 | 02:24:21.646 | ≈02:24:08（客户机钟比宿主快 ~13 s，实为**启动即断**） | `T1 False` |
| BR5 | 02:34:52.982 | 02:35:44（+52 s） | `T4 False` |
| BR6 | 03:31:15.364 | 03:32:02（+47 s） | `Twait4 False` |

BR6 之后另两点也一致：① `timeout 1500` 到点才结束——**SSH 会话全程没有关**，只是再没有字节；② 03:57:07、03:57:43 两次 `echo ALIVE` 在 25 s / 60 s 超时下 **NO-ANSWER**，而 `VMState="running"`。

三种解释在这组数据里**还分不开**，我不给它们排序：
- **(a) 采集器自己没了、管道被样本续着**：BR6 用 `Start-Process -NoNewWindow` 启动样本，子进程**继承同一个 stdout 句柄**——这正好是"会话开着但无声"的形状。可它只解释"谁还持有句柄"，不解释采集器为何在 Twait 第 5 次、即 2.5 客户机秒后就不写了。
- **(b) 客户机整体停摆**：与 §3.13 的 NEM 底座同源；但 P3 已经记过一次我把"饥饿"当结论又被自己的档案否掉（BR1 会话里样本从未运行也刷出同样量级的 TM lag），所以这条**必须先用不带样本的臂量一遍**才允许引用。
- **(c) 通道**：`--line-buffered` 之后（§3.19 附件）同一通道能连续吐 26 行，故不像纯粹的缓冲问题，但没有单独测过。

⇒ **BR7/CTRL2 的改法是按"三种解释各自会被哪一行数据否掉"来设计的，不是加功能**：
1. 采集器**脱离 SSH 会话**：由 `spawn7.ps1` 走 `Win32_Process.Create`，父进程是 WmiPrvSE（复用 §3.2 已验证的非阻塞管线），会话被杀不再可能截断运行；
2. 每行 `AppendAllText` **落到客户机文件**再顺带 Write-Output，主机侧用**独立、可重试的 scp 轮询**收文件，并记下**每次探针的耗时**——于是"慢"和"死"从一句话变成两个数，(b) 与 (c) 直接被这列数分开；
3. 样本自己的 stdout/stderr **重定向到客户机文件**，不再共享采集器的管道，(a) 里那个句柄继承形状就此消失；
4. 循环按**次数**封顶（`round<200`、`WAIT tick<400`）而不是按客户机分钟；
5. 非 callee 窗口读到全零也必须打一行 `ZEROWIN`——BR6 那版会把"读到 0 字节"静默算进 `5/5`，正是记忆里那条"0 项当通过"的形状；
6. 每窗口的非零字节数改由 C# 侧 `NZ()` 原生统计。原来用 PowerShell 管道在 512 字节上数零，**每轮要走上千个管道对象**；这会不会就是"看起来像客户机卡住"的来源，交由 CTRL2 判（同一采集器、样本不上盘、不启动）。

## 4.15c 取件通道：离线只读挂盘**成功**，并把 `CTRL3` 改判（`C53`）

`CTRL3` 那一轮 18 次 `scp` 全部 `handshake-abort`，按 §4.15b 的口径这足以说"通道不行"。本夜把最后一招（离线读盘）做完之后，这个结论**被推翻了一半**——不是因为通道活了，而是因为**我们要取的那个文件从来就不存在**。

**通道本身：可行。** 配方是：关机 → `clonemedium` 把本次会话的差异盘合并复制成 VHD → `diskpart` 执行 `attach vdisk readonly` → 复制出来 → `detach` → 删副本 → **才**回滚。三个坑全是仪器级的，且都当场抓到：
1. 用 `cat << EOF` 写的 diskpart 脚本是 **LF 结尾**，DiskPart 对这种文件**整份拒绝且不指名是哪一行**（只印"无法识别这些命令"）；
2. 改成 CRLF 之后仍然同样报错——**Git Bash 把 diskpart 的 `/s` 开关重写成了 Windows 路径**。要 `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`。
   ⇒ 与 §4.15b 的教训同源：**丢 stderr / 把工具报错读成"环境不可用"**。这次两处都写进 `arm14.sh` 的断言里（脚本先自证 CRLF，再跑）。
3. 结果实测：克隆 49,356,069,376 B、挂载 ~7 s、卷自动出现为 `F:`（普通 NTFS，**无 BitLocker**）、`detach` rc=0、副本删除后 E: 回到 163 GB 空闲。**全程只读挂载，没有写客户机盘、没有碰任何快照。**

**盘身份控制位（先于任何阴性结论）**：挂载盘上 `C:\ept_core\Hardware.exe` 读出 `32,671,232 B / sha256 CFA6998E…`，与登记的 genB 一致；`health.ps1` 首行与我方推入的文件一致。**这条控制位存在的理由**：在挂错的盘上读"没有采集器文件"，与在真盘上读，长得一模一样。

**于是 `CTRL3` 改判：**
- 家目录里**只有 `health.ps1`（04:57:29）晚于快照时刻**；`spawn7.ps1`、`br7.ps1`、`br7_stream.txt` 在 6 个可能落点（home、`C:\ept`、`ept_obs`、`ept_core`、`Windows\Temp`、`Users\Public`）里 **0 命中**。
- ⇒ **采集器从未落盘、从未运行**。`arm12` 的 push 是"发完不管"的（`vm put … >/dev/null 2>&1`），它断在 `health.ps1` 与 `spawn7.ps1` 之间，而 18 次重试取的是一个不存在的文件。
- ⇒ **那 18 个 `handshake-abort` 不再是"取不出文件"的证据**（超时在"文件不存在"和"管道死了"两种情况下长得完全一样）；但它反过来给了一个更值到的上界：**SSH 在 04:57:29 还活着、在下一次 push 之前就死了**——这比任何重试循环都更紧地夹住了"通道什么时候死"。
- ⇒ **BR7 的取件前置条件改由离线通道满足**，判据一字未动；改的是：所有输入必须在开机后头几分钟内推完并**逐个 sha256 回读验证**（`arm17.sh` 的 phase 3），运行期完全不依赖活通道。
- 代价与限度，写在用之前：这是一条**尸检**通道——看不到瞬态，样本自己抹掉的东西读不到；硬关机可能丢掉未刷盘的**尾部**（所以采集器必须逐行 flush，`br7.ps1` 已经是）；一臂约 2 分钟关机+克隆、49 GB 临时空间、10 秒挂载。

| `0x1407a21d7..e2` | `mov r8d,0x100` / `lea rdx,[rbp+0x230]` / `mov rcx,rsi` | 三参：目的对象、缓冲、长度 256 |
| `0x1407a21e8` | **`call 0x14117c32e`** | **落点**。`C38` §4 早就把它标成 `[RG2 window (captured)]`——只是同件那句阴性让我没回头看这行 |
| `0x1407a21ff..` | `mov ecx,0x100` / `rep stosb` | 交出去之后**立刻把 256 B 缓冲抹掉** |

⇒ **观察**：P3§3.5 的"每跳 +256 B、首 32 字节逐运行不同"现在有生成方式了——块**不是整段拷贝**，而是 256 次逐字节混合（熵源＝§4.14 的状态字 + 4 个壳侧调用），长度由 `cmp edi,0x100` 钉死。
⇒ **一条顺带的负面结论**：缓冲交出后马上清零 ⇒ "在进程内存里扫到一份现成追加块"从设计上就不成立。**这直接改变 BR6 那两条"两页读回全零"该怎么读**：全零不再是"该处还没被写到"的强证据，也可能是"写过又被抹"。范围声明：这条只适用于 `0x1407a21ff` 抹的那个栈缓冲 `[rbp+0x230]`，不适用于 `0x141a1ff1b`／`0x1417612fa` 那两页本身。

### (3) 落点 `0x14117c32e` 的字节已经在手上（`C51`），但判"是不是明文"翻了一次车

从 RG2 blob（`0x140e00000..0x141200000`）里按 VA 直接切出 0x140 B 反汇编：**83 条**、结尾 `ret 8` + 11 字节 `int3` 对齐填充；形态是 VMProtect **变异垃圾**（`pushfq`/`popfq` 成对、`not byte ptr [rsp+0x20]` + `setae` 打在同一个栈槽字节上、`movabs` 一个大常数进未使用寄存器）夹真指令（`lea rsp,[rsp+0x28]`、`mov qword ptr [rsp+0x10],rbx` 这类影子区溢出）。**11 个调用目标全部落在 held 头之外**（`0x1415…`～`0x141d…`），其中 `0x141a10a2b` 与阻断出口返回值 `0x141a1ff1b` 落在**同一个 64 KB**（`0x141a1xxxx`）。

## 4.18 追加：闸门支配性——一次"想把它关掉"的尝试，以及它测出来的结构事实（`C52`，纯离线）

§4.16-4 里那条限制（"按地址序的最后一处写**没有证明支配**"）本夜试图用 CFG 支配树关掉。**结论：关不掉；但这次失败把原因从"我没算"换成了"边不在这段字节里"**，并且顺带纠正三条我自己的判据。

### (1) 三条被自己的对照否掉的代理判据

| 我打算用的判据 | 为什么不算 | 换掉之后 |
|---|---|---|
| "没有任何跳转落进 `(xor, 闸门]` 区间" | 太严：命中的 12 处**全是区间内部**的分支，内部分支不构成旁路 | 改成真正的支配树（Lengauer-Tarjan 之外的迭代式 Cooper-Harvey-Kennedy） |
| "区间内出现 `r12` 字样即视为写" | 方向错：`mov qword ptr [rsp+0x30], r12` 是**读** `r12` | 只看**目的寄存器** ⇒ `main` 全函数共 **20 处** `r12` 目的写，区间 `(0x1407a7449, 0x1407a7afd]` 内 **0 处** |

⇒ 第二条是有实质收益的：**C48 那句"比较点之前最后一次写是 `xor r12d,r12d`"从假设升级为已检阴性**（仍受解码完整性界住：覆盖式 98.0 %）。

### (2) 支配树：控制位全过，但闸门所在的块从入口不可达

`main = 0x1407a4b90..0x1407aa710` 覆盖式解出 6,323 条指令 ⇒ **849 个基本块**、664 条直接转移、3 条间接转移。控制位：**入口块支配全部 274 个可达块**（算法对自身平凡情形自校）、闸门那条跳转到 `0x1407a7b4f` 的指令按**目标**找到了 12 处（含 `0x1407a7af3 jne`，正是我记忆里"闸门第一条件的出口"）、`0x1407a7449` 确实是指令起点且 `op_str` 正确。**而四个闸门比较（`a7aec/af5/afd/b06`）所在的块，从 `main` 入口不可达。**

### (3) 为什么不可达——这才是本轮的真正产出

- `main` 的 **438 个 `call` 没有一个指向自己区间内**（去向：`.text` 他处 211、`.Sq>` 210、其他映射 17）⇒ 那 78 个"孤儿块头"**不是被调体**，"函数体内嵌套小函数"这条解释被否掉；
- 78 个孤儿块头里被任何直接转移点名的：**0 个**；每一个的前驱在地址序上都是一个以 `jmp`(42 次) 或 `ret`(36 次) 收尾的块；
- 可达块里"没有后继"的只有 6 个，其中 3 个正好坐在不可达代码上面（`0x1407a56ca ret 0x41cc`、`0x1407a6ef7 jmp`、`0x1407a7bef ret 8`）。
⇒ **观察**：`main` 这段"函数体"在字节层面**不是一条连通的流**——它的入边由 `.Sq>` 里的分发持有（VMProtect），另有 3 条间接转移目标未知。
⇒ **因此**："xor 必然先于闸门执行"**既不能从 `.text` 证明、也不能从 `.text` 否证**。要关它需要那 3 条间接转移的目标（正是 BR7 窗口清单要够到的壳侧页），或一次直接观察比较结果的运行。这条限制从此不再是"我还没算"，而是"算它需要手上没有的那一页"。
⇒ 顺带否掉一种讲法：既然 `main` 内没有任何直接转移指向那四条比较指令，"闸门是由某个可见分支选出来的"在 `main` 内部不成立（无论支持还是反对）。

### (4) 一个数一遍才发现的错

我先前写"两处 `ret 0x41cc` 连着出现"，那是**同一个 stub 形状重复**被我从 0x140 字节窗口里读成两处。实测：`c2 cc 41` 在整个 `main` 里只出现 **1 次**（`0x1407a56ca`）。规则：**形状重复不等于计数**，任何"N 处"必须来自全函数普查而不是窗口目测。

## 4.19 追加：B1 的被调方地址与当前观测边界（`C55`/`C59`，臂 BR7Q/BR7R）

### (3) 当前地址结论：调用点真实存在，但被调方不在捕获窗口
`C59`（`<HOST_PATH>\vmctl\verify_sq_callees_corrected.py` 生成，输入为 `stream_text.bin` 与可用的 RG2 blob）在 `VA=0x140000000+stream_offset` 下逐字节解析所有 `E8 rel32`：

### (4) 于是"阻断是否也终止进程"现在能说的三句
1. **"读字节 + 反汇编"这条路闭合不了它**：`.Sq>` 可读但不可直接解成 x86（第 2 节，带正负对照）；两个调用点地址真实存在，但被调方本体在当前捕获窗口之外（第 3 节）。要判调用点的语义，需要 devirtualize（超出本 lab 的手段与授权），或改用行为判据。
2. **一条有界的正面观察**：样本在前 **40 guest-秒**内不退出（`WAIT tick=…  exited=False` 一路到底），而进程在 `age=7 s` 时还能被 `ReadProcessMemory` 命中 11 个窗口。若终止块真被执行、`int3` 被默认处理器接住，进程应当在走到那里时立刻死掉并交出退出码。⇒ 终止块**至少没在这 40 guest-秒内走完**。这不是"分支＝继续"的证明（VMP 里可能正在磨），但它把"取不到退出码"的原因从"臂不够长"改写成了"**进程在前 40 guest-秒内不退出**"。
3. **两条不依赖退出码的行为判据已埋在同一臂里**：`CLEAN_PRE/CLEAN_POST`——阻断叶子的动作集合是 `rmdir /s /q {C,D}:\Windows\System32\{Logs,HardwareLogs}`，而本机（同 19045 构建）`System32\Logs` **确实存在**，所以 PRE=Y→POST=− 就是分支留痕；`WINSTA responding=… title=…`——检验"样本卡在模态对话框上"这一条，它同时解释为什么六臂谁都拿不到 `EXIT`。BR7S 三次尝试的读数（同一脚本 `br7s.ps1`，每轮只动仪器）：**S1** 回包给了 `CLEAN_PRE=Y--- D:vol` 和 `HOSTS=NOT-pinned`，随后**样本在未钉住的状态下被启动**——那是我的脚本只"检查"没"执行"边界的后果，见 P3§3.2 行 32 与 P5§5.8，该臂不作任何分支读数。护栏修好后：**S2** 回包 0 B、`/ept` 属性 0 条、取件正对照 `NEWFILE_COUNT=0`；**S3** 两次投递都在 `kex_exchange_identification` 处 `Connection reset by peer`，VM 变成 **aborted**（12:23:05，与子盘最后一次写入同一秒），`NEWFILE_COUNT=0`。⇒ **行为判据这条路今天拿不到读数**：`arm14` phase 6c 那两行（`Logs PRESENT items=1` / `HardwareLogs ABSENT`）在 `NEWFILE_COUNT=0` 之下**只是基线复述，不能读成"清理支未执行"**——我自己写下的 K3 规则在这里挡住了这次误读。
