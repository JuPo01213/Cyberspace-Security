# EPT 项目代理规则

## 核心概念对齐（2026-09-27 用户讨论沉淀 · 最高优先级）

**本项目所有结论、实验设计、文档表述都必须先对齐以下概念，否则后续会重复踩坑。**

### 1. “校验结果为真” 与 “自然授权” 不是一回事

样本的“校验通过”不是一个孤立的布尔值。自然卡密流程中，校验通过后样本自己的算法会**同时产生一批真实状态**（解析字段、派生数据、会话/许可信息、机器绑定结果等），后续代码消费的就是这批状态。

| | 校验结果 | 伴随的派生状态 | 后续代码运行前提 |
|---|---|---|---|
| 输入真卡密 | 样本算法独立算出“是” | 完整、真实 | 完整授权前提 |
| 调试改写判定 | 外部强制为“是” | 缺失、为空、或错误 | 残缺/错误前提 |

**结论**：把外部判定写成“是”≠ 自然授权。因为校验通过后本该产生的状态没有真实生成，后续行为很可能不完整或走偏（实测：强制放行后仍 `IsLogin=0`、`GetServerOption=-3`，最后 FatalExit）。

### 2. 三种手段必须明确区分（证据中必须逐轮标注）

```text
自然授权 (natural authorization)
    样本原始代码未经任何外部改写，靠自身校验逻辑独立判成功并继续。
    唯一可称为“自然授权成功”的情形。

受控放行 / 联网校验反转 (gate reversal, controlled bypass)
    外部做了最小、可回滚、运行时作用域的改动（如反转“联网失败→退出”分支），
    使样本进入后续路径继续运行。
    结果是“受控放行下观察到的真实行为”，不是自然授权成功。

伪造授权 (forged authorization)
    直接写授权状态全局、把校验函数 patch 成恒成功、伪造响应。
    属于被禁止冒充自然授权的手段。
```

**关键推论（用户讨论结论）**：把“校验结果”从“否”改成“是”并触发后续动作，**不构成自然授权**——因为伴随的派生状态是空的、错的。但这不阻止我们做**受控放行**来观察后续真实行为；只是结论必须标注为 `real_sample_guest_run_with_gate_reversal`，不得写成自然授权。

### 3. 为什么“结果相同”不等于“行为等价”

- 自然授权：校验算法独立产出“是” + 完整派生状态 → 完整后续行为。
- 强制放行：只有判定“是”，派生状态缺失 → 后续行为可能缺失/偏差。
- 因此不能用“触发了解码动作”反推“授权是自然的”。触发 ≠ 自然。

### 4. 当前流程定位（用户确认的操作流程）

```text
解锁框输入卡密 → 主程序内再次输入卡密 → 触发程序 → 联网校验 → 正式启动本地程序
```

- 卡密/本地授权部分：已解决（如何解决按既有证据独立记录，不默认自然通过）。
- **主闸门 = 联网校验阶段**：实测 `SP_Verify_GetServerOption=-3` →「服务器校验失败！」→ `FatalExit`。
- 目标：反转“联网校验失败→退出”分支，使样本进入本地主流程，**不截断地观察后续真实恶意行为**。

## 分析目的与完成方向（校正 · 2026-09-27）

本项目的分析对象是一份**恶意样本**（`<HOST_PATH>\EPT\sample\EPT专业游戏维修工具箱V5.1.exe` 及其派生的 `Hardware.genB.exe` 等）。它无法、也不应以正规授权流程运行。历史几轮分析把“解码 separation 判据”误当成终点，导致方向偏离；本文件据此校正目的与完成方向：

1. **解码不是目的，只是触发点。** 对 RC00/RC03/RC06 的还原（XOR 流、validator、`+0x80` 写回）只是理解了“解码 seam 怎么工作”，不构成分析完成。
2. **解码必须在真实样本程序内自然执行，并继续越过 RC06 进入后续路径。** 真实目标进程的控制流、栈/内存和后续行为必须来自样本自身；响应来源必须单独标注：自然驱动 response 属于自然运行，I/O 边界受控注入只能作为 `real_sample_guest_run_injected_io` 研究手段。受控注入不是自然驱动响应，不能写成真实授权成功。把解码函数抽离到 Python/harness 单跑（如 C152/C175）**不能**算作目标级完成。
3. **真正的分析目标是解码之后：**
   - 解码真实发生后产生的变化——尤其 `caller+0x80` 写入的 268 字节被谁消费、以何种方式被使用；
   - 以及随后的**伪装 / 规避 / 持久化等行为**（进程注入、驱动或组件释放、文件/注册表改动、网络回连试探、痕迹清理等）。
4. **不能破坏解码后的行为。** 注入响应、必要的授权/联网闸门放行等前置手段允许，但**放行后程序必须继续自然运行**，不得在 RC06 处停下；所有放行后行为都应被真实观察、记录，而非被截断。
5. **完成判据（校正）：** 同一次真实样本 Guest 运行中，必须同时取得：
   - 解码 seam 在真实目标代码路径中发生（`target_native_return==0x1`、`target_caller_diff_bytes>0`、命中切口、caller `+0x80` 前后缓冲，并记录自然 response 或受控注入来源）；
   - **以及** RC06 之后自然产生的行为证据（进程/线程、文件/注册表、网络尝试、关键内存差分、注入/释放产物等），且这些行为确为真实程序在解码后自然产生、未被我们在 RC06 或首个行为点截断。
   仅满足下方“真实样本 seam 的必要条件”而缺少解码后行为证据，记为“解码 seam 局部闭合 / 行为未观察”，**不是完成**。

## 样本上游与项目边界

**`<HOST_PATH>\EPT` 是本分析工作的唯一样本上游和样本身份权威。**

- 待分析的原始样本位于 `<HOST_PATH>\EPT\sample\`；脱壳、重建和其他派生物位于本仓库约定的派生目录。
- 本工作涉及的所有 `EPT`、`Hardware.exe`、`Hardware.genA`、`Hardware.genB` 或其他样本副本，都必须能够追溯到 `<HOST_PATH>\EPT\sample\` 中的样本，或由该样本在受控环境中派生出来。
- 仅凭文件名、目录名、旧日志、旧 writeup 或“看起来相同”不能证明样本身份。使用派生物前必须记录来源路径、完整 SHA-256、派生步骤/运行编号和当前版本状态。
- 无法证明来自 `<HOST_PATH>\EPT\sample\` 的文件一律视为**外来或身份未知材料**：不得把它作为当前样本运行、反汇编、动态验证或结论依据。
- `<HOST_PATH>\HexPatch` 不是样本上游，也不能反向定义 EPT 样本的版本、地址、入口、驱动身份或分析结论。

## 两个仓库的职责

### 本仓库：`<HOST_PATH>\EPT`

本仓库负责：

- 样本与样本派生物的身份登记；
- 静态/动态分析的证据；
- `artifacts\evidence\` 中的可审查证据件；
- `writeup\`、`RUN_MANIFEST_genB.md` 和当前分析结论。

本仓库不接收 HexPatch 的构建中间物、探针可执行文件、PDB/OBJ、运行时日志或临时转储作为“样本本体”。这类材料如需引用，只能作为外部实验材料，并且必须附带可复核的来源与哈希。

### 外部仓库：`<HOST_PATH>\HexPatch`

HexPatch 负责其自身的工具工程、探针源码、构建产物和 VM 运行材料。其 `probe\`、`ept-out\`、`ept-run\`、`.ept-*\`、`materials\` 等目录中的文件都是派生/实验材料，不是 EPT 样本身份的权威来源。

在 HexPatch 中产生的文件不能仅凭名称写回 EPT 结论。若要进入本仓库，必须先完成：

1. 与 EPT 样本上游的身份核对；
2. 记录完整哈希和来源；
3. 说明它是样本副本、探针、日志、转储还是解释性材料；
4. 放入本仓库正确的 evidence/captures/deprecated 归属，而不是根目录或样本目录。

## 交叉引用规则

- EPT 分析任务的工作目录默认是 `<HOST_PATH>\EPT`；HexPatch 仅作为明确标注的外部材料目录。
- EPT 任务不得从 `<HOST_PATH>\HexPatch\ept-out\`、`ept-run\`、`probe\` 或 `materials\` 直接选择“当前样本”。必须先回到 EPT 样本上游核对身份。
- HexPatch 探针可以用于验证 EPT 样本的派生路径，但探针代码、构建输出和运行日志必须留在 HexPatch；EPT 只保存可审查的证据摘要和必要的原始捕获物哈希。
- 两边出现同名文件、不同版本或不同地址时，先停止并做样本身份核对，不得按目录名或最近修改时间自动选择。
- 未提交文件、历史稿、双语副本和自动生成报告都不自动拥有规范权威；必须结合 Git 状态、样本哈希和当前运行证据判断。

## 当前主线：本地卡密授权已解决，主闸门是联网校验阶段（2026-09-27 校正）

### 流程定义（按用户确认的实际操作流程）

```text
1. 解锁框输入卡密
2. 主程序内再次输入卡密 → 触发程序
3. 程序进入联网校验阶段
4. 联网校验成功 → 正式启动本地程序（后续真实恶意行为才开始）
```

- **卡密/本地授权部分已解决**：卡密正确时，样本本地授权校验通过，进入联网校验阶段。
- **主闸门 = 联网校验阶段**：实测证据显示该阶段失败时样本走 `SP_Verify_Init=0` → `SP_Verify_GetServerOption=-3` →「服务器校验失败！」→ `FatalExit`（无本地配置的 Setup 路径），或 → 随机服务名 Open/Create/Start ×3 失败 → `FatalExit`（有本地配置的 StoredFlow 路径）。**停在联网判定失败 = 永远到不了本地主流程。**

### 目标与方法

- **目标**：让样本越过“联网校验失败→退出”的本地判定分支，进入真实的本地程序主流程，并继续自然运行，采集后续恶意行为。
- **方法**：对联网校验判定点做**最小、可回滚、运行时作用域**的受控放行——将“校验失败→退出”分支屏蔽或反转，使样本自身逻辑判定联网授权为通过。放行后**不得截断**，继续观察样本自然产生的后续行为（服务/驱动/持久化/文件/注册表/进程等）。
- **这不是伪造真实授权，而是受控前置放行**：我们没有写“授权状态全局=成功”，没有把 `CardLogin` 等 patch 成恒成功；我们只反转“联网失败→退出”这一个本地判定分支，让样本自己的主流程代码继续执行。
- **不连接任何真实服务器**：不连 `yz.hwid001.com`，不伪造真实服务响应冒充自然授权。反转的是样本内部的失败分支判定，不是真的完成了网络通信。
- **必须记录**：闸门原始返回值/分支、放行点、放行动作、目标代码页前后状态、样本 SHA-256、运行编号、`evidence_scope`。

### 运行格式

```
真实 child 身份/入口确认
  → 本地卡密输入确认（已解决部分按既有证据复用）
  → 联网校验判定点定位（SP_Verify_GetServerOption / 服务器校验失败 / FatalExit 上游）
  → 确认原始返回值与失败分支
  → 对可回滚运行副本做最小临时放行（反转失败分支）
  → 不暂停、不截断，继续采集联网校验后行为
  → 若到达 RC00/RC03/RC06，继续按 seam 必要条件记录并越过
```

### 状态判定必须诚实

- 卡密未通过、联网校验判定点未定位或未放行时，记 `AUTH_GATE_UNRESOLVED` / `NETWORK_GATE_HELD`，不得写成“解码失败”或“授权成功”。
- 联网校验已放行但样本仍未进入本地主流程时，记 `DEBUGGER_NOT_REACHED` 或 `MAIN_FLOW_UNOBSERVED`。
- 反转联网分支后样本进入了真实主流程并产生后续行为，这是**受控放行下的真实行为**，必须标注放行来源，不能写成“自然联网授权成功”。
- 唯一可称为自然授权成功的判据：样本自身原始代码未经任何内存/返回分支反转，就在一次运行中完成了全部校验并继续执行。用计划任务 `\Microsoft\Hardware`、`System32\Logs`/`HardwareLogs` 等外部可观标志辅助判定。

## 目标优先与实验选择

- 本项目目标由上方校正后的最终验收定义；规划时从同一 Guest 运行必须取得的目标 seam、解码后消费者、行为证据和运行归因倒推，而不是以静态分析数量、断点命中、runner 准备或环境检查作为进展。
- 允许使用可回滚的联网/授权闸门放行或 I/O 边界受控 response 注入来让真实目标进入后续路径；这些手段必须在证据中显式标注，且不得改写、截断或替代 RC06 之后的行为。被动观测和通信检查只用于解决明确阻断问题，不能替代目标验证。
- 每轮动态实验必须有唯一可证伪假设、相对既有证据的新信息点、单次运行的验收字段、短硬 deadline、收尾方式和停损条件；复用已证实结果，不重复无信息增益的地址、断点或失败流程。
- 若观测方案不能在同一运行中读取目标返回值、caller 缓冲区前后内容并计算变化字节数，或不能确认被观测进程与 EPT 权威样本谱系的关系，不得把该轮描述为业务闭环实验；先修正方案，不以 marker/timeout 补足缺失证据。
- 同一轮证据不闭合时明确标记未完成/未知；不得将宿主 harness、不同 VM 运行、静态推断或磁盘哈希拼接为 Guest 目标成功。连续无新增信息时停止该分支并切换到基于既有证据的新假设。
- **目标优先，文档从简（2026-09-24 用户校正）：** 当用户要求继续推进样本分析时，不得把时间主要用于批量新增证据件、台账、writeup 或重复性说明。已完成运行只保留原始收割物和必要的短摘要；除非用户明确要求交付文档，否则先推进能直接增加目标级信息的只读定位或受控实验。不得为了“看起来有进度”新增文档替代真实 seam/后行为证据。
- **阶段反思与沉淀（2026-09-27 收敛）：** 每轮失败先保留该 run 的原始事实与必要短摘要，不因单次故障立即修改 Skill、台账和多份说明。只有当经验同时满足“通用、可复用、已被真实运行验证，且不是当前样本特例”时，才作为 candidate lesson 在阶段结束或复发确认后晋升到 canonical Skill。反思不是阻断性任务；优先恢复实验主线，避免记录和维护重新压过目标实验。

### 授权/联网闸门的定位必须运行时定位，不靠静态地址硬编码

- 旧候选地址（`0x1407a3080` 等）曾在多轮中不命中，不能作为必然闸门；从“联网校验失败分支”（`SP_Verify_GetServerOption`、服务器校验失败弹窗、`FatalExit` 上游、StoredFlow 服务创建循环）的运行时实测定位判定点。
- 定位手段优先只读：`ba e 1`（硬件执行断点，不写内存、不插 0xCC）在判定点返回处观察并做最小放行；放行后不截断，继续采集后续行为。
- 仪器禁忌（避免重犯）：不得对 `ntdll!NtCreateFile`/`NtOpenFile` 使用带内存解引用的条件断点（如 `poi(poi(@rcx+0x10)+8)`）——会造成 `Memory access error`，属**仪器故障**而非行为阴性。

## 真实样本 seam 的必要条件（非最终完成判据）

涉及 RC00/RC03/RC06 的目标级实验，以下只是**必要的 seam 观测条件**，不是项目最终完成条件：

```text
同一次真实样本 Guest 运行中：
  target_native_return == 0x1
  target_caller_diff_bytes > 0
```

其中：

- `target_native_return` 必须来自真实 EPT 派生目标进程在该次运行中的目标调用返回；`validator_rax`、Python 返回值或 harness 返回值不能代替它。
- `target_caller_diff_bytes` 必须是同一真实目标进程 caller 结构的可靠 before/after 内存差异计数；输出长度、写入尝试、`caller_output_written=true`、harness 自己的结构差异不能代替它。
- 必须同时保留真实命中切口、caller `+0x80` 前后缓冲、响应来源/注入位置、样本 SHA-256、VM/快照、运行编号和清理状态。
- 只命中 F060、接缝被打桩、校验器返回 1、生成了不同哈希或进程存活，都不能单独证明真实样本解码完成。

### 证据范围与禁止的同名字段映射

每个运行产物必须显式写出 `evidence_scope`，至少区分：

```text
real_sample_guest_run                           真实样本/真实目标进程运行
real_sample_guest_run_with_gate_reversal         真实目标进程运行，但仅受控反转了联网/授权失败分支（最小可回滚放行）
real_sample_guest_run_injected_io               真实目标进程运行，但 I/O 响应在已确认边界受控注入
host_mapped_code_runner                         宿主映射代码段/受控 stub runner
caller_injection_harness                        caller/injection 级 harness
offline_reference_synthetic_response            离线参考模型/合成 response
synthetic_device_boundary                       合成句柄、control code 或无效设备参数
```

只有 `real_sample_guest_run` 或明确标注的 `real_sample_guest_run_with_gate_reversal` / `real_sample_guest_run_injected_io` 才能使用目标级字段 `target_native_return`、`target_caller_diff_bytes`；harness/参考实现必须使用 `harness_*` 或 `reference_*` 前缀。禁止以下等价映射：

```text
validator_rax / harness_validator_rax       != target_native_return
harness_decoded_output_bytes                != target_caller_diff_bytes
caller_output_written                       != target_caller_diff_bytes > 0
c_struct_changed_bytes                     != target_caller_diff_bytes
RC06 success in harness                    != real-sample RC06 completion
DeviceIoControl API hit                     != driver accepted request
output != input                             != real decode
联网校验分支被反转                           != 自然联网授权成功
```

闸门反转的运行必须单独记录：它可以让**真实目标进程自己的主流程**继续运行，用于研究授权/联网校验后的行为；但反转不是自然授权，不能写成真实授权成功或自然网络响应。若该运行在 RC06、异常点或其他位置被终止，则不得声称已观察到解码后自然行为。

> 以上 seam 条件只是“解码在目标进程中被观测到”的必要非充分条件。最终完成还要求同一次运行继续通过 RC06，并取得解码后自然行为证据。caller/injection 级 harness（C152/C175）即便满足其本地回归条件，也不计入目标完成。

## 执行与安全边界

- 原始样本不得直接修改；所有补丁、放行和探针实验使用可回滚副本，并保留原始哈希。
- 样本执行、主动反汇编、解密、转储复原和动态行为验证遵守本项目既有的 VM-only 规则；宿主只做编排、取证拷贝、证据整理和文档维护。
- 不连接任何真实 C2/生产服务器；不在分析中把“反转本地联网失败判定”写成“完成了真实网络通信”。
- 发现来源不明、样本混用、证据互相冲突或结论已被撤回时，先标记为未知/作废并隔离，不得为了保持旧叙述而拼接结论。
