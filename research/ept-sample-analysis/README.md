# EPT 授权靶场与逆向分析仓库

本目录是一个用于**授权安全研究、样本逆向分析和分析方法沉淀**的工作仓库。它既保存受控分析对象和逆向过程，也保存证据、阶段结论、失败记录与复盘材料，目标是让一次分析能够被复核、继续推进，并逐步沉淀为可复用的工作方法。

本仓库只用于获得授权的研究环境和靶场，不面向真实生产系统、真实 C2 或未授权目标。

## 仓库承担的三类工作

### 授权靶场

仓库中的样本用于隔离环境中的受控实验。实验应在可回滚的 Windows Guest/VM 中进行，宿主侧只负责编排、取证收割、证据整理和文档维护。原始样本保持只读，运行时修改、放行和探针只能作用于可回滚副本。

### 逆向分析

仓库记录从样本身份确认、解包、静态分析、动态调试、通信边界观察到后续行为验证的完整链路。分析对象可能包含外层启动器、内嵌业务层、下发或释放的核心程序，以及与它们相关的进程、服务、文件、注册表和网络行为。

当前 EPT 样本的重点不是证明“正规授权成功”，而是理解真实样本在授权/联网判定之后的行为。联网校验失败时，可以在明确标注的受控实验中使用最小、可回滚的 gate reversal 或 I/O 边界响应注入，让真实目标继续运行；这类结果必须写成“受控放行”或“受控响应下的真实行为”，不能冒充自然授权。

### 经验与复盘

失败的安装、通信、调试、收割和证据归因同样是研究材料。复盘的目的不是维护旧结论，而是说明：

- 哪些现象是真实样本行为，哪些只是仪器、通信或环境故障；
- 哪些局部验证不能代表目标级完成；
- 哪些流程减少了等待、返工、人工操作和跨运行拼接；
- 下一次实验应保留什么、删除什么、改变什么。

## 样本、派生物与公开范围

本地 EPT 工作区中的 `sample/` 是样本身份的权威来源。原始样本、解包树、运行副本、补丁、探针、harness、转储和日志不是同一种材料；每个派生物都应能追溯到原始样本、派生步骤、运行编号和完整哈希。

本 GitHub 条目是经过整理和脱敏的公开副本，主要提供分析文本、方法说明和小型可审查证据件，**不把原始样本字节、内存转储、完整 pcap、反汇编工程或凭据提交到公开仓库**。公开副本不能反向定义本地样本身份，也不能替代本地运行证据。

## 证据语言

分析记录必须区分以下几种状态：

- **自然授权**：样本原始代码未经外部改写，依靠自身校验逻辑完成授权并继续运行。
- **受控放行 / 受控响应注入**：对运行副本进行最小、可回滚的运行时干预，使样本越过失败闸门或收到受控响应。它用于观察真实后续路径，但不等于自然授权。
- **伪造授权**：直接写入授权状态、强制校验恒成功或伪造许可/响应状态。它不能作为自然授权证据。

目标级结论必须来自同一次真实目标 Guest 运行。对当前 EPT 任务而言，`target_native_return==0x1` 和 `target_caller_diff_bytes>0` 只是解码 seam 的必要条件；还必须继续越过 RC06，并在同一运行中取得解码后消费者和后续行为证据。宿主 harness、映射代码运行器、离线合成响应、超时 marker、进程存活或单独命中断点，都不能替代这条证据链。

每轮运行使用唯一 `run_id`，记录样本谱系、哈希、VM/快照、响应来源、注入位置、证据范围、收割物和清理状态。不同运行的局部结果不能为了形成完整故事而拼接。

## 目录概览

| 路径 | 用途 |
|---|---|
| `sample/` | 本地权威样本及可追溯的样本身份材料 |
| `unpack/` | 解包、重建和静态分析工作产物 |
| `writeup/` | 面向阅读和交付的分析章节、结论与证据账本 |
| `artifacts/evidence/` | 小型、可审查的证据件，通常使用 `C<n>_*` 命名 |
| `artifacts/captures/` | 内存窗口、pcap、Ghidra 对象等原始捕获物；公开仓库通常不提交 |
| `artifacts/deprecated/` | 已作废或证据不足的产物，以及作废原因 |
| `runs/` | 每轮运行的 `run.json`、事件日志、收割物和结果分类 |
| `patches/` | 运行副本的可回滚补丁和补丁材料 |
| `method/` | 项目工作流、通信约定、证据规则和阶段复盘 |
| `config/` | 工具链、环境和项目配置；动态运行事实以各轮 run 记录为准 |
| `archive/` | 已冻结的历史分析材料 |
| `AGENTS.md` | 项目执行契约、边界和当前有效规则 |
| `LAYOUT.md` | 文件归属、命名、公开范围和整理规则 |

宿主执行器、一次性探针和可再生脚本不应在仓库中复制出第二份权威实现；它们应保存在宿主工具目录，并在运行记录中登记版本和来源。

## 推荐阅读顺序

1. `AGENTS.md`：先了解样本身份、实验边界、证据语义和运行门禁。
2. `README.md` 与 `LAYOUT.md`：了解仓库定位、目录职责和材料归属。
3. `writeup/00-index.md`：查看章节索引、结论入口和历史更正。
4. 相关 `writeup/` 章节：按静态证据、动态证据、授权/通信路径和后续行为阅读。
5. `method/`：了解当前适用的工作流、通信重构和复盘结论。
6. `RUN_MANIFEST_genB.md` 及 `runs/` 中具体运行记录：确认某一轮实际做了什么、留下了什么证据。
7. `artifacts/evidence/`：回到具体证据件核对结论，而不是只依赖叙述。

README 只承担稳定的仓库入口说明；当前阶段、PID、时间、返回值、快照、运行结果和“是否完成”等动态事实，以对应的 `run.json`、事件日志、收割物和阶段文档为准。

## 安全与治理边界

- 原始样本不得直接修改；所有补丁和运行时干预必须作用于可回滚副本。
- 样本执行、主动反汇编、解密、转储复原和动态行为验证遵守 VM-only 边界。
- 不连接真实 C2、生产服务器或真实授权服务；公开材料必须脱敏。
- 不把工具、通信、调试器或收割器成功误写成样本业务成功。
- 运行失败、通信失败、仪器无命中、超时和样本业务阴性必须分别分类。
- 不提交凭据、token、私钥、完整样本字节、敏感网络数据或不必要的大型原始捕获物。
- 新增材料前先确认其归属和生命周期；不要在根目录散落临时脚本、截图、日志或重复副本。
- 修改本仓库前先阅读项目规则并检查现有权威文件，避免建立第二套流程或第二份事实来源。
