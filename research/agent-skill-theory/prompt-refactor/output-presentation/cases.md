# 输出表达与排版 Few-shot

## 连续论述不要拆成视觉碎片

场景：需要解释为什么两个模块不应继续拆分，论证本身只有一条连续因果链。

不理想：把每一句话放成一个单独段落，再用多个“原因”“结果”“结论”小标题分开。

正确：用一到两个完整段落保持因果关系连续；只有进入真正不同的边界或反例时再分段。

## 标题表达语义层级，而不是程序编号

场景：一篇说明包含核心原则、边界和几个案例。

不理想：
“1. 核心原则 / 2. 边界 / 3. 案例一 / 4. 案例二”。

正确：仅在有助于定位时使用语义标题，并通过 Markdown 层级表达从属关系；案例不因出现顺序而机械编号。

## 列表有明确扫描收益时再使用

场景：三个候选方案需要比较各自的实际后果。

正确：可以使用一个紧凑列表或小表格帮助横向扫描。

反例：如果内容是一条连续推理链，不把每个论点强行变成 bullet。

## 避免二维滚动表格

场景：十二个属性、二十个对象，其中大部分单元格都是长句。

错误：建立一个超宽超高表格。

正确：先按真正影响判断的维度分组，用正文说明；只有仍需直接比较的少数稳定维度保留在小表格中。

## 普通说明不要塞进代码块

场景：需要强调一句行为原则。

错误：仅为了视觉突出，把普通自然语言放进代码块。

正确：保持正文或必要的行内强调；代码块只保留需要精确字面结构的内容。

## 案例先给完整场景

不理想：
“观察：失败。原因：工具错误。指导：换工具。”

正确：先说明任务目标、当时已有能力和实际采取的方法，再分析为什么该选择有问题以及规则应如何指导未来行为。
