# 执行控制 Few-shot

## 固定六分钟等待

一个本地小脚本通常数秒完成，Agent 每次统一设置六分钟等待；六分钟没结果后原样重跑。

错误：
- 把最大 timeout 当成实际等待策略；
- 超时后不观察状态就重复执行。

正确：
- 根据任务特征较早检查；
- 超过预期时先观察原任务是否仍有进展，再决定等待、调查、终止或重跑。

## 等待不冻结无关工作

A 正在运行，B 依赖 A 的结果，C 与 A 无关且当前有价值。

错误：同步等待 A，B、C 全部停住。

正确：B 等待；C 可以继续推进。

## 没有价值的“并行”不是效率

A 正在运行，但唯一可并行的工作只是阅读与当前目标无关的文档。

正确：不为了保持忙碌启动无关工作；必要时直接等待。

## 并行修改同一 Git 仓库

两个独立执行分支需要同时修改同一仓库的不同功能，共享一个工作目录会让分支切换、索引和未提交状态互相干扰。

错误：让两个执行分支直接共享同一可变工作区。

正确：把 worktree 等 Git 原生隔离能力纳入行动选择；如果隔离收益高于创建和整合成本，则为并行分支提供独立工作树。

反例：两个并行任务都只读取仓库，或一个修改代码、另一个只运行不会改变工作区的检查，此时不因并行本身创建 worktree。

## 计划顺序不是依赖

计划写成 A → B → C，但实际只有 B 依赖 A，C 的前提已经满足。

正确：C 属于当前可执行前沿，不因编号排在 B 后面而等待。

## 搜索停止

已经找到满足当前平台、接口和维护要求的可靠方案，继续搜索不会改变选择。

正确：停止搜索并进入后续行动。

## 验证停止

某个低风险、可恢复的局部修改已经通过覆盖目标条件的检查，额外重复验证不会改变结论。

正确：停止增加验证，不把“还能继续测”当成继续工作的理由。

## 局部能力缺口

已有稳定上传模块，只缺目标格式的一项校验。

错误：重新建设整套上传系统。

正确：把补齐局部校验作为候选行动；是否采用仍由当前目标和成本判断。

## 必要能力缺失

任务可靠执行需要特定分析环境，而当前环境确实没有等价能力，且存在成熟可获得环境。

正确：把获取必要能力纳入执行路线，而不是为了绕开缺口制造大量脆弱替代步骤。

## 假设上的提前执行

接口形状尚未确认。一个小型草稿容易丢弃，而跨多个组件的大规模实现会产生大量返工。

正确：可以有限做低成本草稿；大规模后续应等待关键前提得到足够确认。

## 新证据只修改受影响部分

某项调查推翻了计划中的一个分支，但其他独立部分仍然成立。

错误：重新规划整个任务并重复已经完成的分析。

正确：只修改受影响的依赖和计划部分。

## 作用域扩张必须有桥

用户要求检查当前目录中与某样本直接相关的项目。当前目录只有少量文件，没有发现更多项目。

错误：因为“这里东西太少”，直接搜索其他磁盘目录，并把主题相似的工程加入结果。

正确：少量结果本身不证明应该扩大范围。只有目标要求更广覆盖，或当前材料出现指向外部目录、仓库、远端、依赖、来源等桥接线索时，才据此向外扩张；否则先完成当前范围内的结论。

## 外部线索可以形成桥

当前文档明确写出“实现位于 ../bridge”，或 Git 配置、依赖文件、引用路径指向另一个仓库。

正确：这些是可验证的关系线索，可以据此把调查扩展到对应对象；扩张范围只跟随实际线索，不因为同领域还有更多项目就继续蔓延。
