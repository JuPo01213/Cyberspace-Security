# Git 治理

Git 是持续维护型工作区的默认版本治理能力。涉及代码、文档、配置、Skill 或其他长期资产的修改时，应主动检查当前工作区是否已经由 Git 管理，而不是等待用户提醒。

已有仓库时沿用现有历史与边界；尚未纳入 Git、且工作区具有持续维护价值时，应主动把建立 Git 管理纳入执行选择。是否实际初始化、创建分支、使用 worktree 或执行其他 Git 操作，由执行控制根据当前任务决定。

执行 Git 操作前，读取仓库当前状态以及用户级、项目级规则和记忆中的 Git 偏好，并遵循已经形成的约定，不重复询问已有答案。

当前有效内容只维护一个权威版本，历史演化交给 Git。不要为了保存旧状态创建 `v2`、`v3`、`final`、`backup` 等平行副本；只有多个版本本身需要长期同时存在且具有独立语义时才例外。

修改前区分已有变更与本次任务产生的变更，不覆盖、丢弃或错误归属现有工作。首次纳入版本控制前，确保密钥、凭据、缓存、构建产物、日志和临时文件等不应进入历史的内容被正确忽略。

Git 提供 branch、worktree 等原生隔离能力，可用于相互独立或并行工作的状态隔离；这些能力的具体触发条件和调度决策由执行控制负责。

提交以有意义、可理解、可回退的状态变化为单位，不机械提交每个微小动作，也不把彼此无关的修改长期堆积在同一提交中。提交说明遵循用户已有偏好。

Git 保存长期资产的演化，不是 Agent 的运行日志。需要了解旧状态、变化原因或历史演进时优先查询 Git，而不是把历史不断复制回当前权威文件。

本地版本治理与远端操作分开处理。使用 Git 管理本地历史不自动意味着可以创建远端、公开发布、推送或覆盖远端历史；这些行为仍服从对应授权。

核心原则：**当前工作区保存唯一有效状态，Git 保存其演化；Agent 主动承担版本治理，而不是把是否使用 Git 的判断责任留给用户。**
