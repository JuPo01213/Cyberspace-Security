# 策略自检与反思 Few-shot

## 有专用能力却持续走笨路线

任务只是获取网页公开文本，能力状态已经表明存在直接网页抓取能力，但执行多次选择交互式浏览器手动获取。

策略自检不新增“网页任务禁止浏览器”这种特例。它应检查：为什么已经可用的专用能力没有进入正常行动选择。

如果现有执行规则已经要求利用更直接的已有能力，则问题不是缺少同义规则，而是该规则没有在行动选择时实际生效；strategy delta 应针对触发、优先级或调用位置，而不是再写一条网页专用补丁。

## 六分钟等待反复出现

执行控制已经明确规定等待和检查应根据实际任务特征决定，但 Agent 仍把一个统一的长 timeout 当成默认等待周期，并在多次任务中重复这种模式。

反思不再增加“某类脚本只能等多少秒”的规则。它应识别：已有动态等待策略没有约束实际行为，并产生针对该策略生效方式的修正候选。

## 一次偶发失败不是策略缺陷

一个正常可靠的工具因临时网络故障失败一次。

正确：更新认识状态并由执行控制决定下一步；没有证据表明选择该工具的策略本身有稳定缺陷，不形成长期 strategy delta。

## 局部补丁暴露共同原因

连续几个问题都通过增加特殊分支解决，但这些分支最终都源于同一个错误的输入假设。

正确：策略反思应优先修正共同假设或产生该假设的规则，而不是继续为每个表面症状增加例外。

## 现有规则已经覆盖

Agent 犯错后发现 Prompt 中早已有明确规则禁止这种做法。

错误：再追加一条措辞不同但语义相同的规则。

正确：把问题定位为规则未生效，检查其触发、优先级、位置或与其他规则的冲突，使已有 owner 真正约束行为。

## 用户纠正是证据，不是前提

用户指出某种做法明显绕路。

正确：把纠正作为策略异常的强证据进行复查；但同类问题即使用户没有看到，固定策略自检仍然应能够发现。

## 具体事故不能决定抽象边界

某次浏览器操作低效。

错误：固化成“永远不要使用浏览器”。

正确：抽象到能够解释为何该次行动选择失配的策略层原因，同时保留需要交互、动态 UI 或视觉判断等情况下浏览器仍可能合理的边界。

## “相关”被悄悄改成“有用”

任务要求定位与当前对象实际相关的项目。执行过程中因为当前目录结果较少，搜索逐渐扩展到其他目录，并开始用“主题接近、研究价值高”作为纳入标准。

正确：策略自检应识别这不是单纯“搜多了”，而是行动策略把目标中的关系判据从“存在实际关联”替换成了“可能有用”。strategy delta 应回到真正的语义 owner：目标模型保持关系含义，认识状态要求关系证据，执行控制要求作用域扩张存在桥接依据；反思模块本身不再新增一条项目搜索特例。
