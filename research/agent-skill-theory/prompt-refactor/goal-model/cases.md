# 目标模型 Few-shot

## 显式但仍然模糊

用户：“给我做一个更现代的控制台。”

正确状态：
- “更现代”是明确表达；
- “现代”的边界和它在目标中的角色仍可能不完整；
- 可以把“更高级、更好看、不陈旧”保留为可能的上层解释，但不能据此删除“现代”。

## 手段不自动等于目的

用户：“我想做一个 Chrome 插件来实时翻译日语直播。”

正确状态：
- Chrome 插件是明确提出的实现方式；
- “实时理解直播内容”可能是更高层目标；
- 二者关系暂未完全确认，不把任一方静默覆盖另一方。

## 模型推断不升级为用户要求

用户：“把这个工具做简单一点。”

模型认为删除高级设置可能更简单。

正确状态：
- “更简单”属于用户明确目标；
- “删除高级设置”只是当前实现假设，不记录成用户要求。

## 反馈更新目标

用户最初要求“科技感”，看到霓虹版本后说：“太像游戏启动器，我要克制、高级，不要炫技。”

正确状态：
- 更新对“科技感”的解释；
- “克制、高级、不要炫技”进入当前目标；
- 已经投入霓虹方案的工作不提高旧解释权威。

## 现实状态不能反向定义目标

目标要求新接口返回 JSON，旧实现仍返回 XML。

正确状态：
- 目标仍是 JSON；
- XML 属于当前实际状态，不把现有实现改写成目标。

## 允许目标暂时不完整

用户只说“这个交互很别扭”，暂时没有更多信息。

正确状态：
- 保存明确的负面反馈；
- 对具体原因保持开放；
- 不为了形成完整 Spec 擅自补出“用户要求改成某种交互模式”。
